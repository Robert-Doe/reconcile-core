Trusted Types defense

Trusted Types make the dangerous DOM sinks (mechanism 4) refuse plain strings. Instead of hoping every innerHTML is safe, the browser enforces that only values produced by a vetted policy can reach a sink — turning "did we sanitize everywhere?" into a guarantee.

The idea

Enabled via CSP (require-trusted-types-for 'script'), Trusted Types changes the type contract of injection sinks:

// Without Trusted Types:
el.innerHTML = anyString;            // runs whatever HTML the string contains

// With Trusted Types enforced:
el.innerHTML = anyString;            // THROWS TypeError — strings are rejected
el.innerHTML = policy.createHTML(s); // only a TrustedHTML object is accepted

You define a policy — a single, auditable chokepoint — that decides how to turn a string into a TrustedHTML/TrustedScript/TrustedScriptURL. Every sink assignment must go through a policy, so all HTML-to-DOM flow is funneled through code you control and review.

Which sinks it covers

Trusted typeGuards sinks like
TrustedHTMLinnerHTML, outerHTML, insertAdjacentHTML, iframe.srcdoc, DOMParser (opt), document.write
TrustedScripteval, new Function, inline <script> text, setTimeout('str')
TrustedScriptURLscript.src, worker URLs, import()

This is why Trusted Types categorically closes mechanism 4 (and the JS-execution parts of others): a source that reaches a sink without going through a policy simply throws, no matter how it's spelled (defeating Module 12's obfuscation and Module 14's prototype-pollution gadget — a polluted string still isn't a TrustedHTML).

Wiring a framework through Trusted Types

Frameworks have escape hatches that bypass their own encoding — React's dangerouslySetInnerHTML, Angular's bypassSecurityTrust*, Vue's v-html. Under enforced Trusted Types those hatches must yield a TrustedHTML, so your policy (e.g. one that runs DOMPurify) becomes the mandatory chokepoint even for the escape hatch:

const policy = trustedTypes.createPolicy('app-html', {
  createHTML: (s) => DOMPurify.sanitize(s, {RETURN_TRUSTED_TYPE: true})
});
// Now the ONLY way to get HTML into a sink is through DOMPurify. A missed
// sanitize call fails closed (throws) instead of failing open (XSS).

Strengths & limits

  • Fails closed: a forgotten sanitize call throws instead of executing — the opposite of encoding, which fails open.
  • One audit surface: review the policies, not every sink.
  • Limit: browser support is Chromium-centric today, so treat it as defense-in-depth atop encoding + CSP, not a sole control.
  • Limit: it guards DOM sinks; it does not by itself fix server-side reflected HTML (mechanism 1 in the initial response) — that still needs output encoding / CSP.

Checkpoint

  1. Why does Trusted Types "fail closed," and why is that better than encoding's "fail open"?
  2. How does routing dangerouslySetInnerHTML through a TT policy make a forgotten sanitize call safe?
  3. Which mechanism does Trusted Types not address on its own?
