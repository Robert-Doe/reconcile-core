Sanitizers: Compare & Contrast defense

When you genuinely must accept rich HTML (comments, wiki, email), you need a sanitizer. This page runs the same payloads through four strategies and shows which leave a live event handler — the difference between structural safety and hope.

The four strategies

Why textContent wins when you can use it

Most "HTML" inserted into pages is actually just text that a developer reached for innerHTML to place. If you don't need tags, textContent (or createTextNode) makes injection impossible — there is no parse, so mechanisms 1/2/5 cannot fire. The best sanitizer is not needing one.

Choosing and configuring a real sanitizer

  • Prefer DOMPurify or the native Sanitizer API — both operate on the DOM and are mutation-aware, unlike string/regex approaches.
  • Allowlist, don't denylist, tags and attributes. Default-deny everything; permit a small known-safe set.
  • Handle namespaces (SVG/MathML) explicitly or disallow them (Module 07).
  • Keep it updated — mXSS gadgets are found and patched continually (Module 13).
  • Return Trusted Types (RETURN_TRUSTED_TYPE: true) and enforce TT so a missed call fails closed (previous page).
  • Sanitize at the sink, for the sink's context — not once at input (Module 10).
