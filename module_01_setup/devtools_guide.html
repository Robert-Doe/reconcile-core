Browser DevTools as a Weapon

DevTools is where you see the truth: not the bytes you sent, but the DOM the browser actually built from them. Master these six panels and you can dissect any XSS.

Open it

F12, or Ctrl+Shift+I (Windows), Cmd+Opt+I (macOS). Right-click → Inspect jumps straight to an element.

1. Elements — the built DOM (not the source)

This is the single most important distinction in the whole course:

View Source (Ctrl+U)Elements panel / Inspect
The raw bytes the server sentThe live DOM tree the parser constructed
Static textReflects JS mutations, error recovery, normalization
Shows your literal payload stringShows what that string became
Why this gap is the attack surface. When you send <p><p></p>, View Source shows three tags, but the Elements panel shows the parser silently rewrote them into properly nested nodes. Mutation XSS (Module 13) is entirely about payloads that look inert in the source string but become dangerous once the parser rebuilds them. You can only see that in Elements.

2. Console — run JS as the origin

The Console executes JavaScript in the page's origin. Use it to probe sinks directly before you try to reach them through injection:

// Where does user input flow? Inspect a suspected DOM sink live:
document.getElementById('output').innerHTML = '<img src=x onerror=alert(1)>';

// Read what an attacker would steal (in the real target, this is the payoff):
document.cookie
document.domain

// Watch a source you can control:
location.hash

The Console also shows uncaught errors — a broken payload often throws here, telling you exactly which character ended your injection early.

3. Network — what really crossed the wire

Reload with the Network tab open. Click a request to see:

  • Request URL / payload — confirm your parameter arrived unmangled.
  • Response — search it for your payload to confirm reflection and see the surrounding context (Is it inside an attribute? A script? Between tags?). Context decides your break-out.
  • Response Headers — is there a Content-Security-Policy? A Content-Type? A Set-Cookie with HttpOnly? These tell you which defenses (Module 17) are in play.

4. Sources — set breakpoints on sinks

For DOM XSS (Module 09) you must trace a source → sink flow in client code. In Sources you can:

  • Set a line breakpoint where the app reads location.hash / location.search (the source).
  • Use an Event Listener Breakpoint or a DOM breakpoint (right-click a node → Break on → subtree modifications) to catch the moment a sink writes your data.
  • Step through to watch tainted data travel from source to innerHTML/eval.

5. Application — cookies, storage, the loot

Under Application → Storage you see Cookies, Local/Session Storage, and their flags. Note per cookie:

FlagWhat it means for an attacker
HttpOnlyJS cannot read it via document.cookie — pushes the attacker toward request-forgery instead of theft (Module 15).
SecureOnly sent over HTTPS.
SameSiteLimits cross-site sending — a CSRF control, not an XSS one. XSS runs same-site, so SameSite does not save you.

6. The "search the response" habit

Global search across all loaded resources: Ctrl+Shift+F. Drop a unique marker like zZq9 into every field, submit, then search all responses for zZq9. Every hit is a candidate reflection — and the surrounding bytes tell you the context you must break.

Attacker workflow, condensed

  1. Map reflections with a unique marker + global search.
  2. Read the context in the Network response and the Elements DOM.
  3. Diff source vs. DOM — did the parser change your bytes?
  4. Probe the sink live in Console before crafting the injection.
  5. Confirm impact scope in Application (what cookies/storage would you own?).
Defender's inversion. Every one of these steps has a mitigation that would blind the attacker: contextual output encoding kills step 2, a strict CSP kills execution, HttpOnly shrinks step 5. Keep a running note of "which DevTools observation would this defense erase?" — that note becomes your Module 18 gap analysis.
