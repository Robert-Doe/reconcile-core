Module 01

Environment Setup & How to Think Like an Attacker

Before you can defend an origin, you have to be able to attack a copy of it that you own — and read the browser the way an attacker does.

1. What you are building

A single, intentionally-vulnerable web app on http://localhost:5000 that you fully control. Every later module adds either a vulnerable endpoint or a tutorial page to this same origin. Keeping everything on one origin is not laziness — it is honest, because XSS is fundamentally an origin-scoped bug: the whole game is getting JavaScript to run inside a target's origin so it inherits that origin's trust.

3. The one idea that makes XSS make sense: the Same-Origin Policy

The browser isolates content by origin, defined as the triple (scheme, host, port). Two pages share an origin only if all three match exactly:

URL AURL BSame origin?Why
http://localhost:5000/ahttp://localhost:5000/b✅ yesscheme+host+port identical
http://localhost:5000https://localhost:5000❌ noscheme differs (http vs https)
http://localhost:5000http://localhost:5001❌ noport differs
http://localhost:5000http://127.0.0.1:5000❌ nohost string differs (even though it resolves the same!)

The Same-Origin Policy (SOP) stops origin A's script from reading origin B's cookies, DOM, or responses. XSS is the bug class that defeats SOP from the inside: if an attacker gets their script to run as origin B, SOP now protects the attacker's code. Every cookie, every logged-in session, every same-origin fetch is theirs. That is why "just an alert box" is never the real threat — the alert only proves the attacker owns the origin's trust.

Mental model. Ask of every feature: "Can attacker-controlled bytes reach a place where the browser will treat them as code running in this origin?" That single question is the whole course.

4. The attacker's loop (how to think)

  1. Find a reflection or sink. Where does my input come back out — in HTML? in an attribute? in a URL? in a JS string? Or does client code read my input and hand it to a DOM API?
  2. Identify the context. The same payload behaves differently in HTML text vs. inside an attribute vs. inside a <script> vs. inside a URL. Context decides the escape you need.
  3. Break the context. Supply the exact bytes that end the current context and start a code-bearing one (a quote, a >, a javascript:).
  4. Prove execution. Land a harmless alert(document.domain). If it pops, arbitrary JS runs in this origin — full stop.
  5. Then think like a defender. What single control would have made step 3 impossible regardless of payload? That is the question your PhD answers.
