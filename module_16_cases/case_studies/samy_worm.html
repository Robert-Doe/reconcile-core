Module 16 · Case Study

The Samy Worm — MySpace, October 2005

The fastest-spreading malware in history at the time: ~1,000,000 friend requests in under 24 hours, forcing MySpace offline. The prototype of the self-propagating stored-XSS worm.

What happened

Samy Kamkar found that MySpace profile pages let users include some HTML/CSS for styling but tried to strip scripting. He bypassed the filter and stored JavaScript in his own profile. When any logged-in user viewed his profile, their browser ran the script, which:

  1. Added "Samy" as a friend of the viewer.
  2. Appended "but most of all, samy is my hero" to the viewer's profile.
  3. Copied the worm's own source into the viewer's profile, so anyone who then viewed that profile was infected too.

Step 3 is the payload that matters: self-replication turned a stored XSS into an exponential worm.

The mechanisms & filter bypasses (why it worked)

MySpace's filter removed <script> and many keywords. Samy's code is a museum of Module 05 / Module 12 techniques:

ObstacleBypass usedCourse module
<script> strippedUsed a CSS/expression + event-handler vector instead (mechanism 2)M05
The word javascript blockedSplit across a newline: java\nscript — the browser reassembled it (mechanism 3 + decode boundary)M06/M12
innerHTML blocked as a literalBuilt via eval('document.body.inne'+'rHTML')-style string concatenationM12
Quotes were escapedUsed String.fromCharCode() to avoid literal quotesM12
Same-origin request needed to post the updateXMLHttpRequest to the profile-edit endpoint, replaying the CSRF token read from the page (mechanism 4 + Module 15 chaining)M15

Note how it combines every theme of the course: an event-handler mechanism, decode-boundary evasion, string-reconstruction, and a same-origin forged request that re-used the page's own anti-CSRF token — the exact chain you built in Module 15.

The absent defenses

  • Contextual output encoding on profile HTML (a denylist filter was used instead of encoding — Module 12's core lesson).
  • CSP did not exist yet; a script-src without 'unsafe-inline' would have stopped inline execution outright.
  • Re-authentication / robust anti-automation on profile edits; the worm replayed the CSRF token trivially because it ran same-origin (Module 15).
  • Rate-limiting / anomaly detection on the friend/edit endpoints would have slowed propagation.

Reconstruct it safely in your lab

Below is a de-fanged mini-worm for the Module 10 comment board (/comments). It contains no real malice: when a viewer loads an infected comments page, their browser posts one new comment containing the same worm plus a visible marker, and pings your Module 11 callback. That is enough to watch the propagation curve. It is rate-limited to one repost per page load and tagged so you can clean up.

The mini-worm payload (post it once as a comment body)

The WORM_PLACEHOLDER is where the worm's own source goes — a true quine is fiddly; for the lab it is enough that each infected view posts a marker comment and a callback so you observe the spread. Use the generate button below to build a self-reposting version, then post it at /comments.

Watch propagation: after posting once, reload /comments a few times (each load = one "visitor") and watch new samy comments appear and hits pile up in /callbacks. To clean up, run make clean (deletes the comment DB) or restart the lab.

Why Samy still matters for your thesis

Samy is the canonical demonstration that stored XSS + self-replication scales super-linearly, and that denylist filtering fails against a determined attacker. Any defense you propose in Module 18 should answer: would it have stopped Samy at the encoding layer, the execution layer (CSP/Trusted Types), or the propagation layer (re-auth/rate-limit)? The strongest proposals stop it at more than one.
