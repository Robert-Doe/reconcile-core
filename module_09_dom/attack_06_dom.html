Module 09 · Mechanism 4: DOM sinks

DOM-Based XSS & Client-Side Sinks attack

The payload never touches the server. Client JavaScript reads a source it doesn't control and hands it to a sink that treats strings as code or markup. Server-side filters are blind to it.

The source → sink model

DOM XSS is a taint-flow bug: attacker-controlled data flows from a source, through the program, into a dangerous sink, without being neutralized on the way.

Why <img onerror> and not <script>?

Recall Module 04: a <script> inserted via innerHTML does not execute — the HTML spec forbids "parser-inserted" script from a fragment assignment. So DOM XSS through innerHTML pivots to mechanism 2 (event handlers) or mechanism 3 (URI schemes). This is a crisp example of the taxonomy guiding exploitation: the sink dictates which mechanism you reach for.

el.innerHTML = '<script>alert(1)</script>';   // does NOT run
el.innerHTML = '<img src=x onerror=alert(1)>';    // DOES run
el.innerHTML = '<svg onload=alert(1)>';           // DOES run

Tracing the flow in DevTools

  1. Sources panel: set a breakpoint on the line that reads location.hash (the source).
  2. Right-click the target node → Break on → subtree modifications (a DOM breakpoint on the sink).
  3. Reload with the payload; step through and watch the tainted string travel source → sink with no sanitization. This is the vulnerability, made visible.

Special sinks worth knowing

SinkNote
eval(x), Function(x)Interpret JavaScript, not HTML. Any source reaching them is instant RCE-in-origin. JSON.parse is the safe alternative to eval for data.
setTimeout('code', t)String first argument is eval-like. Always pass a function instead.
location = x / a.href = xFeeds mechanism 3: a javascript: value executes.
$(userInput) (jQuery)A string starting with < is parsed as HTML — a historically huge DOM-XSS source.
postMessage handler → innerHTMLCross-window messages are attacker-controllable if origin isn't checked.

The defense, precisely

  1. Choose safe sinks: textContent not innerHTML; setAttribute with an allowlisted attribute; build DOM with createElement/append, never string concatenation.
  2. Never feed sources to eval/Function/string timers.
  3. Trusted Types (Module 17) turn these sinks into type-enforced APIs: innerHTML refuses a plain string and demands a TrustedHTML produced by a vetted policy — a capability control that closes mechanism 4 wholesale, which is why it is central to your Module 18 intervention.
  4. Validate postMessage origins and never trust window.name/referrer.

Checkpoint

  1. Why is DOM XSS invisible to a server-side WAF? Prove it with the Network tab.
  2. Why did the payload use onerror rather than a <script> tag?
  3. Which sink is more dangerous, innerHTML or eval, and why? What is the safe replacement for each?
