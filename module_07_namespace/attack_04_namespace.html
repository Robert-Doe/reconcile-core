Tag & Namespace Confusion — SVG, MathML, iframe attack

HTML5 lets SVG and MathML live inline in an HTML document, each with its own parsing rules. Those rule-switches — and the fact that SVG is a scriptable document format — break sanitizers that reason only about "HTML".

Why "it's just an image" is wrong

An SVG file is an XML document. It can contain a <script> element and intrinsic event handlers. When an SVG is served same-origin as image/svg+xml and rendered as a document (you navigate to it, or embed it via <object>/<iframe>, or inline it into the page), that script runs in your origin.

<svg xmlns="http://www.w3.org/2000/svg" onload="alert(document.domain)">
  <script>alert('SVG script runs in ' + document.domain)</script>
  <text x="10" y="20">I look like an image.</text>
</svg>

▶ open the upload page, then click "open (vulnerable)" next to malicious.svg. It is served from /uploads/malicious.svg as image/svg+xml and the script executes in the lab origin.

Inline SVG breaks HTML sanitizers

Inside <svg>/<math> the parser is in foreign content mode (Module 02), where the rules differ from HTML body:

Foreign-content quirkWhy it bypasses sanitizers
Some element/attribute names are case-sensitive (e.g. <foreignObject>, viewBox)A sanitizer that lowercases everything mangles names or misses matches.
<svg> supports its own <script> and event handlers (onload, onbegin on <set>/<animate>)Denylists tuned to HTML tags miss SVG-specific vectors.
Self-closing behaves differently; XML-style /> is honoredTag boundaries a sanitizer computed for HTML are wrong.
<foreignObject> re-enters HTML parsing inside SVGYou can smuggle HTML vectors into a context the sanitizer treats as SVG.
Namespace escape: leaving <math>/<svg> via <annotation-xml encoding="text/html"> integration pointsContent flips back to HTML parsing where the sanitizer already "decided" it was safe.

The MathML one (<mglyph> …) is a famous mXSS seed — the parser's integration-point rules relocate/reinterpret the nested content. You will meet it again in Module 13.

iframe srcdoc — double decoding

<iframe srcdoc="…"> takes an HTML-encoded document as an attribute value. The attribute is entity-decoded first, then the result is parsed as a full HTML document. That double pass lets you hide a script behind entities:

<iframe srcdoc="&lt;script&gt;alert(document.domain)&lt;/script&gt;"></iframe>

A sanitizer that entity-decodes once and inspects, or that allowlists <iframe> but forgets srcdoc is a code sink, is beaten here.

The defensive takeaways

  1. Treat SVG as active content. Never serve user SVG same-origin as image/svg+xml. Serve uploads from a separate, sandboxed origin, force Content-Disposition: attachment + X-Content-Type-Options: nosniff, or rasterize to PNG.
  2. Sanitize on the DOM, in the right namespace. String sanitizers that don't model foreign-content rules (and their integration points) will miss SVG/MathML vectors. DOM-based sanitizers (DOMPurify) that understand namespaces are the baseline — Module 13/17.
  3. Remember srcdoc and data: are code sinks, not benign attributes.
  4. CSP is the backstop: script-src restrictions apply inside SVG documents too.
