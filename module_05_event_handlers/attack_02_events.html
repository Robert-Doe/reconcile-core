Module 05 · Mechanism 2: Event attributes

Event Handler Injection — The Real Workhorse attack

Blocking <script> stops one mechanism and changes nothing about this one. Intrinsic event attributes run JavaScript with no script tag at all — and several fire with zero user interaction.

Why this is the mechanism to master

In the real world, <script> is the first thing filtered and the first thing CSP blocks. Event-handler injection is what actually lands, because:

  • There are 150+ intrinsic event attributes — an enormous long tail no denylist covers completely (see the event catalog).
  • Some fire automatically: onerror on a broken resource, onload on <svg>/<body>, and onfocus combined with autofocus — no click, no hover, no interaction.
  • They live on ordinary, allowlisted-looking tags (<img>, <input>, <svg>), so "images are safe" intuition fails.

The universal fallback: <img onerror>

<img> with a src that cannot load fires onerror immediately. This is the single most reliable payload in the XSS canon because a broken image is guaranteed to error.

Feed the same string to the Module 04 endpoint: /search?q=<img src=x onerror=…>. It fires even though a <script>-blocking filter would let it through — because there is no <script>.

Try each in the sandboxed renderer. Note that none require a click.

Why autofocus + onfocus is special

Most events need the user to do something. autofocus is an attribute that makes the browser move focus to the element automatically on load; that focus is an event, so onfocus fires with no interaction. Combining an auto-firing attribute with a handler is the general recipe for zero-click execution — and it works on form controls that a filter is likely to consider harmless.

The lesson for filters

Consider a filter that removes <script> tags. Against the five mechanisms:

MechanismBlocked by "remove <script>"?
1 Tag parsing (<script>)partially (string match is bypassable — Module 12)
2 Event attributesNO — completely open
3 URI schemesNo
4 DOM sinksNo
5 Escape + reparseNo

A denylist of tags is a denylist against one mechanism, and a leaky one. This is the empirical case for the course's central defensive claim: denylisting loses; you must encode by context or constrain by capability (CSP / Trusted Types).

How the correct defense looks here

If the injection point is an HTML attribute value, the fix is attribute-context encoding: encode ", ', <, >, &, and backtick so the attacker cannot close the attribute or introduce a new one. If the point is HTML text, text encoding prevents the tag from forming in the first place, so no on* attribute is ever created. And a CSP without 'unsafe-inline' refuses to run inline event handlers even if one is injected — a capability control that does not depend on getting encoding perfect. Module 17 measures each.
