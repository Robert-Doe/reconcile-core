Read the tables together. No single deployable defense is ● across all five, and the two that come closest — Trusted Types and "just use textContent" — either need broad browser support + app rewiring, or can't be used where rich HTML is genuinely required. That tension is the research gap.

The residual-risk questions (your thesis targets one)

  1. Mechanism 5 (reparse/mXSS) is only ◐ everywhere. Can a defense be idempotent under re-serialization by construction, so a sanitized value is provably stable across re-parses?
  2. Coverage without an allowlist that drifts: the DOM API grows; sink allowlists and sanitizer configs go stale. Can coverage be expressed against mechanisms rather than an enumerated sink list?
  3. Deployability: Trusted Types is the strongest sink defense but Chromium-centric and rewire-heavy. Is there an in-browser fallback that gives TT-like guarantees where TT is unavailable?
  4. Legacy/no-header contexts: can a purely client-side shim enforce capability controls when the server sends no CSP (the exact gap this lab's default state models)?
