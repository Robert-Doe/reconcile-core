Module 15 · impact

Attack Chaining — XSS → Full Account Takeover attack

This is the module where alert(1) becomes real. XSS is an entry point; the impact is whatever the script does with the origin's trust. Here we chain it into taking over the account.

The mental shift: proof vs. impact

Every previous module ended at alert(document.domain) — proof that arbitrary JS runs in the origin. A defender must understand what an attacker does next, because that dictates which defenses actually reduce risk. Once JS runs same-origin it can:

  • Read document.cookie → session theft (unless HttpOnly).
  • Read any same-origin page → steal anti-CSRF tokens, secrets, personal data.
  • Issue authenticated same-origin fetch requests → forge actions (change password/email, add an OAuth app, transfer funds).
  • Draw a fake login overlay → credential phishing that looks 100% legitimate because it is on the real origin.

The load-bearing insight. Anti-CSRF tokens defend against cross-site forgery — a token the attacker's site cannot read. XSS runs same-origin, so it reads the token trivially. XSS defeats CSRF defenses, and it defeats SameSite cookies too (the request is same-site). This is why "we have CSRF tokens" is not an answer to XSS, and why XSS sits near the top of impact rankings.

The defense, precisely

  1. Prevent the XSS — everything downstream depends on it. This is why the course invests so heavily in mechanisms 1–5.
  2. HttpOnly cookies — removes the easy session-theft link (Step 1), forcing the attacker to on-page forgery.
  3. Re-authentication for sensitive actions (require the current password / a WebAuthn step to change password/email) — breaks the silent forgery in Step 2.
  4. CSP + Trusted Types — stop the script from running or from reaching sinks at all, so no link in the chain forms.
  5. Bind sessions (token binding, short lifetimes, anomaly detection) to reduce replay value of any stolen cookie.
