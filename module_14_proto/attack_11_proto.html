Module 14 · Mechanism 4 (indirect)

Prototype Pollution → DOM XSS attack

An XSS with no injection point. You never control the sink's argument directly — you poison the defaults that innocent code falls back to, by writing onto Object.prototype.

The two halves of the bug

Prototype pollution is only exploitable when a pollution sink meets a gadget:

HalfWhat it is
1. Pollution sinkCode that copies attacker-controlled keys into an object without blocking __proto__/constructor/prototype — typically an unsafe deep-merge, _.set, a query-string parser, or JSON merged into config. Writing obj["__proto__"]["x"]=v sets Object.prototype.x = v, so every object now inherits x.
2. GadgetInnocent code that reads a property which is usually absent, so it falls through to the polluted prototype, and passes the value somewhere dangerous — a DOM sink (innerHTML, src), a config that adds a <script>, an option that becomes a URL, etc.

How __proto__ pollution works (30-second refresher)

const o = {};
o.__proto__.polluted = 'yes';   // writes onto Object.prototype
({}).polluted;                  // 'yes'  — a brand-new object inherits it!
'default' || ({}).polluted;     // truthy defaults now come from the attacker

JavaScript objects inherit from Object.prototype. Write a property there and it becomes a global default for every object that lacks its own copy. Attackers turn a data-merge bug into control over code that reads "missing" options.

The lab gadget

This page loads vuln_spa_proto.js. It has:

// (1) pollution sink: a query parser that walks into __proto__
unsafeParseQuery(location.search);   // ?__proto__[widgetHtml]=... pollutes

// (2) gadget: renders a widget from config, defaulting to a prototype value
function renderWidget(config) {
  const html = config.widgetHtml || 'Welcome to your dashboard.';
  box.innerHTML = html;              // SINK — html can come from the prototype
}
renderWidget({});                    // {} inherits widgetHtml after pollution

The developer believes renderWidget({}) is safe: "the config is an empty object I created; nothing user-supplied." Prototype pollution breaks exactly that assumption.

Why this class is nasty for defenders

  • No injection point to find. Traditional XSS review looks for "where does user input reach a sink." Here the input reaches a merge, and the sink reads a default. The two may live in different files / libraries.
  • Gadgets hide in dependencies. A pollution sink in one library plus a gadget in another (or in a framework's own templating) yields XSS neither library's authors saw. Many real cases are library-vs-library.
  • It bypasses input-focused output encoding. The dangerous value is introduced after your input handling, as a property lookup.

The defense, precisely

  1. Kill the pollution sink: reject __proto__, constructor, prototype keys in any merge/parse; use Map instead of plain objects for untrusted key/value data; create config with Object.create(null) (no prototype to pollute).
  2. Freeze the prototype: Object.freeze(Object.prototype) in a bootstrap script prevents writes to it entirely (measure app compatibility).
  3. Kill the gadget: route DOM writes through Trusted Types so a polluted widgetHtml string is rejected at innerHTML (Module 17) — a capability control that stops the second half even if the first slips through.
  4. Use safe JSON schema / validation for incoming config; prefer libraries hardened against prototype pollution and keep them updated.

Checkpoint
