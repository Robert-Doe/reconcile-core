Module 10 · delivery class

Stored & Second-Order XSS attack

Reflected XSS needs a crafted link per victim. Stored XSS needs nothing: the payload lives in the database and fires for every visitor, automatically, forever — until someone finds it.

Reflected vs. stored vs. DOM (the three delivery classes)

Where the payload livesWho is hitServer sees it?
Reflected (M04)in a crafted URLwhoever clicks the linkyes (in the request)
Stored (this module)in the app's storageevery visitor to the pageyes (at write time)
DOM (M09)in client state / URL fragmentwhoever loads the crafted stateoften no

These are delivery classes, orthogonal to the five mechanisms. A stored XSS still executes via mechanism 1/2/3/5 — storage just changes who gets hit and how reliably.

Key insight: fix on output, not input

A tempting but wrong fix is to sanitize comments before storing. Problems:

  • You must then render in exactly the context you sanitized for — but the same row often appears in HTML, in an attribute, in a JSON API, in an email. One input-time sanitization cannot be correct for all output contexts.
  • Sanitizing on input corrupts legitimate data (a comment literally discussing <script>) and can be bypassed by encoding.
  • Data already in the database (from before the filter, or from another writer) is still dangerous.

The robust rule: store raw, encode/​sanitize at each output for that output's context.

Second-order XSS: safe-at-input, dangerous-at-output

Second-order (a.k.a. stored-in-one-context, executed-in-another) is the subtle sibling. Consider a username validated as "plain text, no SQL injection" and stored fine. Later, an admin dashboard renders that username into an HTML attribute and tag — a different context — without re-encoding:

<!-- /admin/logs renders each author as: -->
<span title="AUTHOR" data-user="AUTHOR">AUTHOR</span>

via /comments, then open /admin/logs. It fires there — in the admin's session — even though the comment board might have encoded it. The payload was inert where it was stored and became active where it was re-rendered.

Why this is dangerous: the victim is often a privileged user (an admin viewing logs), and the attacker never has to visit the vulnerable page themselves. That is the bridge to Module 11 (blind XSS) and Module 15 (chaining to account takeover).

The defense, precisely

  1. Encode/sanitize at every output, for that output's exact context (HTML text, attribute, JS, URL, CSS). Never rely on a single input-time cleanse.
  2. Assume all stored data is tainted, including data written by other services or before your filter existed.
  3. Trace every rendering site of a stored field — the second-order bug lives in the forgotten render site (admin tools, PDF exports, emails).
  4. CSP + Trusted Types as a backstop that does not depend on finding every render site.
