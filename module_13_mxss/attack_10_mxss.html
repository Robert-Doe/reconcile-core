Module 13 · Mechanism 5: reparse

Mutation XSS (mXSS) — The Subtlest Class attack

A string that is provably safe when a sanitizer inspects it, and provably dangerous the moment the browser re-parses its own serialization. mXSS is why string-based sanitization is structurally, not just practically, unsound.

The core inequality

reserialize( parse( x ) ) ≠ x

The HTML parser and the HTML serializer are not inverses (Module 02). A sanitizer typically does: parse → clean the tree → serialize back to a string. It then hands that string to a sink (innerHTML), which parses it again. If the second parse produces a different tree than the one that was cleaned, the cleaning was applied to a tree the browser never actually renders — and a handler can reappear.

Honesty note. Specific historical payloads (the <noscript> and <mglyph> classics) have been patched in current DOMPurify and hardened in browsers. Whether a given string still executes in your exact browser/sanitizer version varies — but the analyzer above still shows the mutation (round-trip instability), which is the durable lesson. New mXSS gadgets are found regularly precisely because the underlying inequality never goes away. Your PhD-grade question: can a defense be idempotent under re-serialization by construction?

Why string sanitizers can't win, structurally

  • They must predict the browser's parse of their output, but the parse depends on context (insertion mode, scripting-enabled flag, namespace) that the sanitizer does not control at the eventual sink.
  • Serialization is lossy/normalizing and not the inverse of parsing, so "clean tree → string" can encode a different tree.
  • The safe fixpoint (a string that parses to itself, forever) is not something a one-shot cleaner can guarantee — you would need to parse-serialize to a fixed point and re-clean each round, which real sanitizers historically did not do.

The defense, precisely

  1. Prefer not to sanitize HTML at all — use textContent and structured DOM construction so no re-parse happens.
  2. If you must accept HTML, use a maintained, DOM-based, mutation-aware sanitizer (DOMPurify) and keep it updated; consider its SAFE_FOR_TEMPLATES / namespace options.
  3. Sanitize to a fixed point: re-parse the sanitizer's output and re-clean until stable (defends the round-trip inequality directly).
  4. Add capability defenses (Trusted Types + strict CSP) so that even a mutation that regrows a handler cannot execute — this is why the strongest posture layers sanitization under a capability control (Module 17/18).
