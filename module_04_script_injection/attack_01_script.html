Module 04 · Mechanism 1: Tag parsing

Script Tag Injection — The Baseline attack

The most literal XSS: the server echoes your URL parameter into the HTML with no encoding, so your <script> becomes part of the document the browser parses and runs.

The vulnerable endpoint

Module 04 adds a /search endpoint (see vuln_reflect.py). Its core bug is one line:

# vuln_reflect.py
q = request.args.get("q", "")
html = PAGE % q          # <-- q is interpolated with NO encoding
return Response(html, mimetype="text/html")

The template puts q into HTML text context:

<p>You searched for: {{ q }}</p>

So whatever bytes you send in q land between two tags, exactly where < starts a new tag (tokenizer Data state, Module 02).

Read the difference in DevTools

  1. Open /search?q=<script>...</script>, then View Source: you see your literal <script> tag in the response bytes.
  2. Open /search-safe?... and View Source: the server sent &lt;script&gt;. The < was encoded to &lt;, so the tokenizer stays in Data state and never opens a tag — it renders the text "<script>" on screen.

That one substitution — < → &lt; — is contextual output encoding, the canonical fix for mechanism 1 in HTML text context. Notice it is a server-side transformation of the output, not input filtering.

Why <script> is the obvious vector — and often blocked

<script> is the first thing every defender thinks to block, so in practice it is frequently filtered, stripped, or CSP-blocked. Three things a serious student must internalize:

FactConsequence
A <script> inserted later via innerHTML does not execute.Reflected injection runs because it is present during the initial parse. DOM-sink injection (Module 09) needs a different mechanism — usually an event handler — because innerHTML won't run raw scripts. This distinction trips up beginners constantly.
Blocking the literal string script is trivially bypassed.Case (<ScRiPt>), split tags, and encoding defeat naive filters (Module 12). And it does nothing to mechanisms 2–5.
A CSP script-src without 'unsafe-inline' blocks this payload even if the HTML injection succeeds.This is why the next thing you learn is that attackers pivot to mechanisms CSP is weaker against, and defenders pivot to Trusted Types + strict CSP (Module 17).

The take-home

Reflected script injection is the hello world of XSS: untrusted input crosses into HTML text context unencoded. The fix (contextual encoding of output) is simple here — but the rest of the course exists because real apps have dozens of contexts (attributes, URLs, JS, CSS, foreign content), each with its own correct encoding, and because attackers have four other mechanisms that this fix does not touch.

Checkpoint

  1. Why does the /search payload execute but the same string set via element.innerHTML would not?
  2. What single character substitution defuses this payload, and why does it work at the tokenizer level?
  3. Encoding fixed mechanism 1 here. Which mechanisms did it not touch?
