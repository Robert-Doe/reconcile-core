The Background / Speculative Pipeline

Here's the part nearly everyone forgets: the browser starts fetching things your markup mentions before the main parser finishes and long before your JavaScript runs. Injected markup can act — leak, forge requests, prefetch — in that gap.

Run this via the lab server (python lab_server.py → /research/track_c_speculative/) so the demos can beacon to the same-origin /collect endpoint and you can see timing. Opened from disk, the explanations still apply but the live fetches won't reach localhost.

C1 · The preload scanner (speculative parser)

While the main parser is blocked (e.g. on a synchronous script), a second, lightweight preload scanner races ahead through the raw byte stream looking for subresources — <img>, <script src>, <link> — and kicks off their fetches early. Two security facts:

  • It sees the static, tokenized markup. Injected <img src> or a dangling-markup URL can begin fetching (and thus exfiltrating) during parsing, before any sanitizer JS runs.
  • It generally can't see content that only later JavaScript injects — so timing determines whether the scanner acts on your payload.

C3 · Speculation Rules API

The modern <script type="speculationrules"> API lets a page declare URLs to prefetch or prerender (fully render in the background). Security model:

  • Prerendering runs a page's scripts in a hidden context — cross-origin prerender is heavily restricted, and prerendered pages are subject to their own CSP.
  • An injected speculation-rules block could prefetch attacker URLs; it is script-tagged, so a nonce CSP that blocks unsanctioned inline scripts also blocks injected rules.
  • State leakage: what a prerender is allowed to read/execute before activation is the security-relevant boundary.
<script type="speculationrules">
{ "prefetch": [{ "source": "list", "urls": ["/next"] }] }
</script>

Why timing is a security property: the same payload string executes, defers, or never runs depending on where and how it enters the parse. A DOM-XSS via document.write(location.hash) injects into the parser stream itself — the preload scanner may fetch its subresources before the handler even finishes.

C5 · CSP & the parser

Where does policy enforcement sit relative to all this speculation?

  • Nonce/hash checks happen as elements are created during tree construction — an injected inline <script> without the nonce is refused at that point, regardless of how it was spelled (defeats obfuscation).
  • strict-dynamic lets a nonced script propagate trust to scripts it creates, removing the need for a host allowlist.
  • The preload scanner vs CSP: the scanner discovers subresources early, but the actual fetch is still subject to CSP fetch-directives (script-src, img-src, connect-src). So CSP can stop a speculative fetch — but only for the directives you actually set. prefetch-src/default-src coverage is the subtle part.
✅ Track F hook
The fallback's threat model must include the speculative phase: a defense that only intercepts innerHTML in your React commit misses a reflected <img src> that the preload scanner already fetched. That's why Track F pairs a sink shim with a strict CSP (connect-src, img-src, base-uri 'none') — the two cover different phases of the pipeline.
