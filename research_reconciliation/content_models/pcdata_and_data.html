PCDATA → DATA: where markup actually happens

This is the content model you already use without knowing its name. Both dials are ON: < opens tags and &amp; decodes. It's the parser's home base — and the only model where an injected < becomes a real tag.

Why "PCDATA" and why HTML5 renamed it

In SGML (HTML's grandparent) PCDATA = "parsed character data": a region the parser must actively parse because its characters might be markup. HTML5 dropped SGML's configurable machinery and hard-coded the behavior into the tokenizer's data state. So: PCDATA and DATA are the same dial setting — both on — one's just the modern name.

The subtle spec phrase worth chewing on: essentially every text node is DATA — but only after parsing. Before parsing, the very same bytes could have been a tag. The content model is what the parser does, not a property the bytes carry.

Case File · the disappearing bold tag

"Why did my <b> turn into an actual bold element?"

A junior dev builds a comment box. They store the literal text a user typed — I love <b>this</b>! — and drop it into the page with div.innerHTML = comment. On screen: this is bold. The user meant the characters <b>; the browser, in DATA, saw a tag and built an element.

Fix: the div is a DATA context, so encode < to &lt; on output. Now the bytes stay text. This is the entire "reflected/stored XSS in HTML text" lesson in one story — the payload just wasn't malicious this time.

Everything else is literal text. Because both are live, DATA is the most permissive model — and therefore the one attackers want their bytes to land in. Every other model turns at least one dial off.

  2. <i>hi</i> &copy; 2026
  3. a &amp;lt; b  (careful — double-encoded!)
Show answers
  1. 5 < 6 && 6 > 5 — entities decode; no real tags (they were encoded).
  2. hi (italic) followed by © 2026 — <i> is a live tag here; &copy; decodes.
  3. The literal text a &lt; b — the outer &amp; decodes to &, leaving the text &lt; (which does NOT further decode — decoding happens once). This "one-pass decode" is a classic double-encoding gotcha (Module 12).

Why DATA is the dangerous model

Injection that lands in DATA is textbook reflected/stored XSS: a < you supply really opens a tag. Every other content model is, for tags, "safer by default" — which is exactly why attackers work to break out of RCDATA/RAWTEXT back into DATA (next pages). The defender's move: in a DATA sink, encode < (and &) so bytes can never become markup.
There are no Dumb Questions
Q: If I set textContent instead of innerHTML, am I still "in DATA"?
A: No — textContent doesn't parse at all; it inserts a literal text node. There's no content model because there's no tokenizing. That's why textContent is the safest sink: it sidesteps this entire module.
Q: Does DATA decode every entity, like &#x6a;?
A: Yes — named (&copy;), decimal (&#169;), and hex (&#xA9;) all decode. This is why a scheme check on a URL must run on the decoded value (Module 06): javascript&colon; decodes to javascript:.
Key points
  • DATA (= PCDATA) has both dials ON: tags open, entities decode.
  • It's the parser's default state and the only model where injected < becomes a tag.
  • The content model is decided by the enclosing element and by the parser's state — not by the bytes.
  • Entities decode once; that's the double-encoding gotcha.
  • textContent has no content model at all — the safest sink.
