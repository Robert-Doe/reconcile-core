RCDATA: the confusing middle

"Replaceable character data." Exactly two elements in all of HTML use it — <title> and <textarea> — and its half-on/half-off dial setting trips up nearly every HTML library ever written.

TAG dial
OFF
<b> is just text
ENTITY dial
ON
&amp; → &

Tags off, entities on. That's the whole rule — and it's the one combination people never expect. The only thing that ends RCDATA is the matching end tag (</title>).

Case File · the browser tab that shouted markup

"Why does my tab literally say <em>Sale!</em>?"

A CMS lets post titles contain HTML — <em>Sale!</em>. On the page (a DATA context, e.g. an <h1>) it renders as Sale! in italics. But the developer also drops the raw title into the document <title> for the browser tab. Because <title> is RCDATA, the <em> is not a tag — the tab shows the literal characters <em>Sale!</em>.

One stored string, two content models, two different correct treatments: render as markup in DATA, but strip-to-plaintext (or entity-escape) for the RCDATA title. This is a content-model flavor of second-order XSS (Module 10): safe in one slot, wrong — or exploitable — in another.

The puzzle everyone gets wrong

What is the title of <title><title></title>?

The title is the literal text <title>. The first <title> opens the element and flips the TAG dial off (RCDATA). The inner <title> is therefore just text, and the </title> closes the element. It's exactly equivalent to <title>&lt;title&gt;</title>.

Dennis Snell's article notes this element's behavior is confused across "all manner of programming languages, platforms, and HTML-parsing code" — because people reach for a regex or an XML parser, and both model RCDATA wrong.

See it: tags stay text, entities still decode

Watch the <title> and <textarea> rows: <b> makes 0 child elements, but &amp; does decode. Half on, half off.

…

Breaking out of RCDATA (the attacker's only move)

Since only </title> ends the region, a payload that contains that literal end tag closes it early and re-enters DATA:

<title>USER</title>
   with USER = </title><img src=x onerror=alert(1)>
→ <title></title><img src=x onerror=alert(1)>   (now DATA — executes)
🔥 Fireside Chat — RCDATA and a Developer
RCDATA
Relax. Inside me, tags are text. Your user's <script> can't hurt you here.
Dev
Great, so I'll just HTML-encode the whole title like I do everywhere else — &lt;, &amp;, done.
RCDATA
Whoa — my ENTITY dial is ON. If you encode a legit & in the title to &amp;, I'll decode it back to & and it'll look right… but if you don't neutralize a literal </title> in the user's text, they close me early. Encode the end-tag sequence, not the whole world.
Dev
So the fix is: encode < (so no </title> can form), and I don't need to fear tags otherwise.
RCDATA
Now you get me.
✏️ Sharpen your Pencil

Predict the exact title text (and whether the entity decodes):

  1. <title><b>Hi</b> &amp; bye</title>
  2. <title>Price: 5 &lt; 6</title>
  3. <textarea></textarea><img src=x onerror=alert(1)></textarea> — does the img execute?
Show answers
  1. Title = <b>Hi</b> & bye. The <b> stays literal (tags off); &amp; decodes to & (entities on).
  2. Title = Price: 5 < 6. &lt; decodes to < — and because tags are off, that decoded < is harmless text, not a tag-open. (Entity-decoded < never starts a tag; only a literal < in the byte stream does.)
  3. Yes. The literal </textarea> closes RCDATA, re-entering DATA where the <img onerror> is live. Classic break-out.
There are no Dumb Questions
Q: Wait — in answer 2, a decoded < is safe, but in DATA it's dangerous?
A: Right, and it's a crucial subtlety. Tags are recognized during tokenizing, from literal < bytes. A < that arrives via entity decoding appears after that decision, so it's inert text in any model. That's why "encode < to &lt;" defuses tags: you replace the literal byte with an entity.
Q: Only two elements are RCDATA? Not <style>?
A: Correct — just <title> and <textarea>. <style> is RAWTEXT (next page): entities are OFF there too. Mixing these up is the #1 escaping mistake.
Key points
  • RCDATA = TAG off, ENTITY on. Only <title> and <textarea>.
  • Tags become literal text; entities still decode. A decoded < is harmless (tags are recognized from literal bytes only).
  • The only exit is the matching end tag — so a literal </title>/</textarea> in user data breaks out to DATA.
  • Defense: encode < so no end-tag can form; you don't need to encode > or fear other tags.
  • Same value in a DATA slot vs an RCDATA slot needs different handling → second-order bugs.
