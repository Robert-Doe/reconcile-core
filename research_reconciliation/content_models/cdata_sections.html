CDATA sections: the two-faced <![CDATA[

Same eight-character opener, opposite meanings depending on where it sits. In XML and inside SVG/MathML it starts a real region of literal text. In plain HTML it isn't a CDATA section at all — it degrades into a "bogus comment." Sanitizers routinely get this backwards.

🔑 First, kill the biggest confusion
"CDATA" (a content model — the result is text) and "a CDATA section" (the syntax <![CDATA[ … ]]>) are not the same thing. As Dennis Snell's article stresses: creating CDATA does not imply creating a CDATA section. A normal XML text node "is CDATA" (it's text) with no <![CDATA[ anywhere in sight.
Case File · the Jekyll-and-Hyde bracket

The content that vanished in HTML but ran in an SVG

A developer copies an XML snippet — <![CDATA[Price < 10 & up]]> — into an HTML page, expecting literal text. Half of it silently disappears (swallowed into a bogus comment). Frustrated, they move the exact same snippet into an uploaded .svg that the app serves. Now it's a real CDATA section — and if the payload were a script instead, it would be live. One string. In HTML: a disappearing comment. In SVG: a fortress of literal text (that can hide a live payload across the boundary).

CDATA sections in three worlds

ContextReal section?What the parser does
XML / XHTMLyesparsing turns fully off; everything up to ]]> is literal text; no entity decoding
HTML — foreign content (inside <svg>/<math>)yessame as XML — a real literal-text section
HTML — everywhere elsenobecomes a bogus comment: reads to the nearest >, makes a comment node; the rest parses as normal DATA

The concrete gotcha, node by node

The same inner content, <![CDATA[But there <em>are</em> tags in here]]>:

  • In HTML: <![CDATA[But there <em> becomes a bogus comment (up to the first >). Then are</em> tags in here]]> parses as DATA — so </em> is a stray end tag and ]]> is just text.
  • In SVG: the whole thing is one literal text node — <em> is not a tag.

HTML
To me? That's not a section. I see <! and start a bogus comment until the next >. Bits of your "secret" leak out as live markup after it.
SVG
To me it's a genuine CDATA section — pure literal text to ]]>. Nothing in it is markup.

So if an attacker can move content from my world into SVG's — or the reverse — its meaning flips. No payload change required.

Why this is a security seam

A sanitizer that "supports SVG" but reasons about CDATA with an HTML mindset (or vice-versa) mis-models where element boundaries are. And because the <svg>/<math> boundary can be crossed via integration points (Track B4), an attacker can shuttle a payload between "CDATA-is-real" and "CDATA-is-a-bogus-comment" worlds. That boundary flip is a first-class mXSS ingredient.

There are no Dumb Questions
Q: If I need a literal & inside an XML CDATA section, can I write &amp;?
A: No — a CDATA section decodes nothing (entities off). &amp; would appear literally as those five characters. Your options: write the raw &, or close the section, emit the entity outside it, and reopen a new section. This is the round-trip catch serializers must handle.
Q: Should I ever use CDATA sections in HTML?
A: Practically never in HTML text — they don't do what people expect (bogus comment). They're meaningful only in XML/XHTML and inside inline SVG/MathML. Treat a <![CDATA[ in HTML source as a probable bug or a probe.
Key points
  • "CDATA" (text result) ≠ "CDATA section" (<![CDATA[…]]> syntax).
  • Real CDATA sections exist in XML and inside SVG/MathML only; in plain HTML the syntax becomes a bogus comment.
  • A bogus comment ends at the first > — so following content can leak back into DATA as live markup.
  • Moving content across the HTML↔foreign boundary flips its meaning — an mXSS ingredient.
  • CDATA sections decode no entities; serializing entity values into them needs the close/emit/reopen trick.
