Content Models · 5 of 7

Security & mXSS Implications

Everything converges here. Almost every content-model subtlety is, from a defender's chair, a way for a sanitizer and a browser to disagree about what a string means — and a disagreement about meaning is the exact definition of a bypass.

🧩 The unifying idea
A content-model mismatch is a parse-differential: two parsers assign the same bytes to different dial settings. One thinks a region is inert text; the other re-enters DATA and forms an element. That gap powers both classic filter bypasses and mutation XSS (Track B6).
Case File · the sanitizer that ran in the wrong world

The <noscript> that was empty to the cleaner, live to the victim

A sanitizer runs in a normal browser tab, where scripting is enabled. It's handed:

<noscript><p title="</noscript><img src=x onerror=alert(1)>">

With scripting on, <noscript> is RAWTEXT — its contents are text — so the sanitizer sees no <img>, declares it clean, and stores it. Later it's rendered where the </noscript> closes early (or scripting is off), the <img> becomes real, and it fires. The sanitizer and the sink were in different worlds — same bytes, different content model, different tree.

The XHTML-vs-HTML escaping inversion

⚠️ A trap for polyglot / migrated templates
In XHTML you must escape <script>/<style> contents (they're PCDATA there — dials on), while in HTML you must not (they're RAWTEXT/script-data — dials off, so an escaped &lt; would render literally and break the code). Serve the "wrong" content-type for a template written for the other and you get either broken pages or injection. The correct escaping is a function of the content model, which is a function of the parsing mode.

Why string sanitizers are structurally fragile

A string sanitizer must predict, for every region of its output, which dial setting the sink will apply — but that depends on the surrounding element, the HTML-vs-foreign namespace, the scripting-enabled flag, and the doctype, none of which it fully controls at the sink. So the robust defenses (Track F) don't operate on strings:

  1. Prefer typed sinks (Trusted Types) — value re-checked at the sink, in its real context.
  2. Sanitize to a serialization fixed point (Track F3) — no residual parse-differential survives.
  3. Sanitize in the same context you'll insert into (Track B5) — never "clean as a <div>, inject into a <table>/<svg>."
  4. Fix the parsing mode — send Content-Type: text/html; charset=utf-8 + X-Content-Type-Options: nosniff so the model isn't decided by sniffing (Track B1).
✏️ Sharpen your Pencil — spot the mismatch

For each, name the content model the sanitizer assumed vs. the one the sink used, and whether it's exploitable:

  1. Sanitizer cleans a value as a <div> fragment; app inserts it inside a <title>.
  2. Sanitizer strips <img> but leaves a user's literal </style>; app renders inside <style>user</style>.
Show answers
  1. Sanitizer assumed DATA; sink is RCDATA. Likely not directly exploitable (RCDATA is more restrictive for tags) but can corrupt display or break out via a literal </title> the sanitizer didn't neutralize. The deeper lesson: the mismatch means the sanitizer's guarantees don't transfer.
  2. Sanitizer implicitly reasoned in DATA (stripping tags); sink is RAWTEXT. Exploitable: the leftover </style> closes RAWTEXT and everything after is DATA. Stripping tags was the wrong tool for a RAWTEXT sink.

Take it to the harness

The content-model payloads (noscript, style-wrapped, CDATA-in-SVG, RCDATA break-out) are exactly the non-idempotent inputs the differential mXSS harness flags. Run them with a candidate sanitizer on/off and watch which models produce a handler that regrows on reparse.

There are no Dumb Questions
Q: If I just always use DOMPurify, do I need any of this?
A: DOMPurify is excellent and handles most of these — but its safety depends on config and version, and new content-model gadgets appear. Understanding the models is how you configure it correctly (e.g. namespace handling), audit it, and know when to layer Trusted Types under it (Track F).
Q: Is "sanitize to a fixed point" real, or hand-waving?
A: Real: re-run the sanitizer on its own output until it stops changing. If sanitize(x) == sanitize(sanitize(x)), no reparse can mutate it further. The harness demonstrates it; Track F3 implements it.
Key points
  • A content-model mismatch = a parse-differential = the seed of a bypass or mXSS.
  • The <noscript> scripting-on/off split is especially nasty for sanitizers (they run scripting-on).
  • Correct escaping depends on the model; XHTML vs HTML even invert the rule for script/style.
  • String sanitizers can't guarantee the sink's model — prefer typed sinks + fixed-point sanitize + same-context sanitizing.
  • Pin the parsing mode with explicit Content-Type + nosniff.
