RAWTEXT, script-data & PLAINTEXT

The "text all the way down" models. Both dials off — no tags, no entities. The parser copies bytes verbatim until one exact end sequence. That verbatim-ness is a gift to attackers and a trap for anyone trying to escape their way to safety.

TAG dial
OFF
everything is literal
ENTITY dial
OFF
&amp; stays &amp;

RAWTEXT — literal until the end tag

Used by <style>, <xmp>, <iframe>, <noembed>, <noframes>, and <noscript> (scripting on). Inside it, <b> is text, &amp; stays five literal characters, and only the matching end tag ends the region.

script-data — RAWTEXT with a maze of side doors

<script> uses "script data": RAWTEXT-like (no entities, no child elements) plus a notorious set of sub-states around <!--, <script, and </script so real JavaScript containing those sequences still parses. Those sub-states are their own bypass playground (script-in-script escaping).

Case File · the stylesheet that ran JavaScript

A "theme color" feature becomes stored XSS

An app lets users pick CSS, and injects it as <style>/* USER */</style>. An attacker submits:

</style><img src=x onerror=alert(document.domain)>

The literal </style> ends the RAWTEXT region; the following bytes are now DATA, and the <img onerror> fires for every visitor.

The developer's instinct — "HTML-encode it like everything else" — fails here, and that failure is the whole point of this page.

The trap: you can't entity-escape your way out of RAWTEXT

Because the ENTITY dial is off, writing &lt;/style&gt; inside <style> does not produce a safe, un-decoded tag — it produces the literal characters &lt;/style&gt; on screen (broken), and it does not stop a real </style> elsewhere in the payload from closing the region. Entity encoding — the tool that saves you in DATA and RCDATA — is useless here. Safe practice: don't put untrusted text in RAWTEXT elements at all. If you truly must, break up the end-tag sequence structurally (e.g. reject/replace </style, </script substrings), never by entity-encoding.
🔥 Fireside Chat — DATA vs RAWTEXT on "just encode it"
DATA
When in doubt, encode < to &lt;. Works great in me.
RAWTEXT
Don't bring that advice into my house. My ENTITY dial is off. Your &lt; shows up as the literal text "&lt;". You didn't sanitize anything — you just uglified it.
DATA
So how does anyone stay safe inside you?
RAWTEXT
You don't feed me untrusted text. Period. Or you physically prevent my end tag from appearing. Encoding is not a lever you have in here.

PLAINTEXT — the one-way door

<plaintext> is the extreme case: it latches. Once the parser enters it, the entire rest of the document is literal text — no end tag, no way back to DATA, ever.

<plaintext><script>alert(1)</script> &amp; everything after
→ one big text node; nothing parses, nothing decodes, forever.
🧠 Brain Power
If an attacker injects a bare <plaintext> high in a page, what happens to all the legitimate markup below it — including a late CSP <meta> or a login form? (It all becomes inert text: a defacement / denial-of-rendering primitive, and a way to neutralize security markup placed later in the document. Content models cut both ways.)
✏️ Sharpen your Pencil

For each, does an alert-capable element end up live? Why?

  1. <style>body{}&lt;/style&gt;<img src=x onerror=alert(1)></style>
  2. <xmp><script>alert(1)</script></xmp>
  3. <script>var s="</script><img src=x onerror=alert(1)>";</script>
Show answers
  1. Live. The &lt;/style&gt; is inert literal text (entities off), so it does NOT close the region — but the real </style> at the end… wait: read carefully. The region runs to the FIRST real </style>. Here the only literal </style> is the final one, so the <img> is inside RAWTEXT → text, NOT live. Trick question! The encoded end-tag proved harmless, and there was no earlier real one. (Change the encoded one to a real </style> and it breaks out.)
  2. Not live. Inside <xmp> (RAWTEXT) the <script> is literal text; the only thing that ends xmp is </xmp>.
  3. Live. The literal </script> inside the JS string closes script-data early (the tokenizer doesn't know about JS strings) — the rest becomes DATA and the <img> fires. This is why embedding user data in inline <script> requires escaping </ (Module E4/SSR).
There are no Dumb Questions
Q: Isn't <noscript> just always RAWTEXT?
A: No — and this is a famous mXSS seed. With scripting enabled (a normal browser tab) <noscript> contents are RAWTEXT (text). With scripting disabled, they're parsed as normal DATA. A sanitizer runs with scripting on and sees text; a different consumer may reparse as markup. Covered on the Security page.
Q: Why does the tokenizer close <script> at a </script> inside a JS string?
A: Because tokenizing happens before JavaScript ever runs — the tokenizer has no idea what a JS string is. It only knows "script data ends at </script." So a </script> in your data is a real region-ender. Escape it as <\/script> in JS strings.
Key points
  • RAWTEXT & script-data = both dials OFF. <style>, <xmp>, <iframe>, <noembed/noframes/noscript, and <script>.
  • Only the literal end tag ends the region — a </style>/</script> in user data breaks out to DATA.
  • Entity-encoding is useless here (dial off) — the defense is to not place untrusted text in these elements, or to structurally block the end-tag sequence.
  • A </script> inside a JS string still closes script-data — escape </.
  • <plaintext> latches: the rest of the document becomes literal text, permanently.
