Track E · Head First · E1–E6

React's XSS Surface

React escapes text and attributes by default. So how does XSS still happen? This track enumerates every place data reaches the DOM bypassing that escaping. The runnable React lab demonstrates each one live, next to the fix.

Run the companion app: cd research_reconciliation/react-lab && npm install && npm run dev. Each section below maps to a component in react-lab/src/vulns/.

E1 · dangerouslySetInnerHTML — the primary sink

The one explicit escape hatch. In the host config it routes straight to node.innerHTML (you saw the exact line in Track D's toy reconciler), so it bypasses all of React's escaping:

// react-lab/src/vulns/E1_DangerouslySetInnerHTML.jsx
<div dangerouslySetInnerHTML={{ __html: userSuppliedHtml }} />
// userSuppliedHtml = '<img src=x onerror=alert(document.domain)>'  -> executes

The name is a warning, not a joke. Any data reaching __html must be sanitized and mXSS-resistant (E6). This is why Track F makes even this hatch pass through a typed policy.

E2 · Auto-escaping and its limits

JSX escapes text children and string attribute values (<, >, &, ", '). It does not understand semantics. The gaps:

GapWhy escaping doesn't helpPayload
href/src/xlink:href URLsa javascript: URL contains no HTML metacharacters to escape<a href={userUrl}> with javascript:alert(1)
style object/stringCSS injection (expression() legacy, exfil via url())style={{background:`url(${x})`}}
<iframe srcDoc>srcDoc is an HTML document sinksrcDoc={userHtml}

Since React 16 a javascript: URL in href logs a warning, and recent React may neutralize some — but this is version-dependent and not guaranteed across all URL props/renderers. Never rely on it; validate the scheme yourself (see react-lab/src/vulns/E2_UrlAndStyle.jsx).

E3 · Prop spreading & injection

<div {...props} /> where props comes from untrusted data is a footgun: whatever keys the attacker controls become attributes/props. If the object contains dangerouslySetInnerHTML, or an attribute-routed handler, or a URL prop, spreading injects it:

const props = JSON.parse(untrusted); // { dangerouslySetInnerHTML: { __html: '<img onerror>' } }
<div {...props} />   // sink reached via spread

ref/handler smuggling: an object shaped like React internals, or a function-valued prop that a component forwards to a DOM node, can reintroduce a handler. Lesson: never spread untrusted objects onto host elements. (See E3_PropSpread.jsx.)

E4 · SSR-specific XSS

Server frameworks embed state in an inline <script> for the client to hydrate. That JSON is not in a React-escaped context — it's raw text inside <script>:

<script>window.__INITIAL_STATE__ = {"bio":"</script><script>alert(1)</script>"}</script>
  • </script> breakout: a string containing </script> closes the tag early. Fix: escape </, <!--, and U+2028/U+2029 in embedded JSON.
  • Framework data blobs: Next.js __NEXT_DATA__, Redux preloaded state, etc. — same class. Frameworks mostly handle it now, but custom embedding is a frequent bug.

See E4_SsrStateEmbedding.jsx (renders both the vulnerable and the correctly-escaped serialization so you can diff them).

E6 · mXSS meets React

The subtle finale. Even if you sanitize the string you pass to dangerouslySetInnerHTML, React just assigns it to innerHTML — and the browser re-parses it. If your sanitized string is not a serialization fixed point (Track B6), the re-parse can regrow a handler. Sanitize-then-React is still unsafe unless the sanitizer is mutation-aware and idempotent.

Why this defeats the obvious fix. "We run DOMPurify before dangerouslySetInnerHTML" is necessary but not sufficient across all sanitizer versions/configs — the mXSS frontier moves. Track F's answer: sanitize to a fixed point and route through Trusted Types so a non-typed value can't reach the sink at all. (See E6_MutationXSS.jsx, which pipes the Track B round-trip oracle over the sanitizer output.)

All four share the same shape: a default-escaped path plus an explicit "trust me" hatch and special-cased URL/HTML sinks. A defense at the DOM sink layer (Track F) therefore protects all of them, which is why the fallback is framed at the host/DOM boundary, not inside React.
