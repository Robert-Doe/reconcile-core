Track A · Head First · A1–A5

DOM Structure & the Inheritance Graph

Before you can say "React escapes this, so it's safe," you have to know what a sink even is and which objects carry it. The answer is an inheritance graph — and the sinks are scattered across it by mixins in ways that make "just audit the sinks" much harder than it sounds.

Why start here? Every defense in Track F ultimately says "no untrusted string may reach a sink." That sentence is only precise if you can enumerate the sinks and know which interface each lives on. This track builds that enumeration from the live browser, not from memory.

A1 · The node-type hierarchy

Every DOM object descends from EventTarget. The security-relevant spine:

EventTarget
 └─ Node
     ├─ Element ─ HTMLElement ─ HTMLAnchorElement, HTMLIFrameElement, HTMLScriptElement, …
     ├─ CharacterData ─ Text, Comment, CDATASection, ProcessingInstruction
     ├─ Document (─ HTMLDocument)
     ├─ DocumentType
     ├─ DocumentFragment ─ ShadowRoot
     └─ Attr

The crucial security observation: sinks are inherited, and they're not uniform across the tree. innerHTML is defined on Element — so a Text node or a Comment simply has no innerHTML. ShadowRoot extends DocumentFragment, which is why a shadow root does get innerHTML (from a mixin) even though a plain fragment behaves differently.

🧠 Brain Power
Assigning textNode.innerHTML = '<img onerror>' — does that create an image element? (No. Text has no innerHTML setter; you're just adding an expando property. The string is inert. This is why moving data to a text node is a safe pattern.)

If your defense hooks Element.prototype.append but forgets that DocumentFragment and Document also get append from the same ParentNode mixin, you have a hole. A3 · Live vs. static collections & DOM clobbering

getElementsByTagName returns a live HTMLCollection; querySelectorAll returns a static NodeList. The live/named-access machinery creates a distinct attack surface: DOM clobbering.

  • Named property access on document and window: an element with id=foo or name=foo can become window.foo.
  • document.forms, form.elements, and element[name] resolve by attacker-controllable names.
  • Injecting markup only (no script) can overwrite a global the app reads — e.g. <a id=config> makes window.config an element, defeating if (window.config) use(window.config.url).

⚠️ The link to React
Clobbering is a no-script primitive that survives HTML sanitizers (the markup is "harmless" tags with id/name). If a React app reads a clobberable global or uses a library that does named lookups, sanitized UGC can still corrupt control flow — a Track E/F concern.

A4 · Shadow DOM & the composed tree

Shadow DOM introduces a second tree that composes with the light DOM at render time. Security-relevant facts:

ConceptSecurity consequence
open vs closed shadow rootsclosed hides element.shadowRoot (returns null) — encapsulation that also hides injected content from your scanners/sanitizers.
slot assignmentLight-DOM nodes render inside a component's shadow tree; a sanitizer that reasons about the light tree misses where content actually lands.
event retargetingEvents crossing the boundary have their target retargeted; handlers that trust event.target/composed path can be confused.
::part/::slottedStyling hooks that cross the boundary — CSS-injection surface.
ShadowRoot.innerHTMLA full HTML-parsing sink (inherited via InnerHTML mixin on ShadowRoot) — Web Components frequently build their shadow tree from strings.

Encapsulation cuts both ways: it can contain a component's XSS to its shadow tree, but a closed root can also hide an injected sink from a page-level defense that only walks the document.

Contrast — the safe members: textContent, createTextNode, setAttribute on a non-URL attribute, append(stringOrTextNode) (appends text, does not parse). The whole game of a defense is: force untrusted data through the safe members, or through a typed chokepoint (Trusted Types, Track F) before it can reach any row above.
