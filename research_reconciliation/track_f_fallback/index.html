Designing the In-Browser Fallback

Everything so far was reconnaissance. Now we build the defense the whole course points at: an in-browser layer that makes untrusted strings unable to reach a sink by construction, holds across the mXSS frontier, and is evaluable. This is your thesis core.

F1 · Threat model & invariants

Assumptions (state yours explicitly).

  • Untrusted data, honest-but-buggy app. The app's code isn't malicious, but it will occasionally forget to sanitize, or a dependency will open a sink. Attacker controls data (props, URL, storage, SSR JSON), not the bundle.
  • Out of scope: a fully attacker-controlled bundle (that's supply-chain, needs SRI/isolation — Track C/Module 16), and native/extension code.

The invariant to enforce:

No value reaches an HTML/URL/script sink (the Track A5 map) unless it is either (a) a policy-produced typed value, or (b) sanitized to a serialization fixed point. Otherwise the sink throws (fail-closed).

F2 · Trusted Types — the backbone

Trusted Types change the type contract of the sinks: with require-trusted-types-for 'script', innerHTML & friends reject plain strings and demand a TrustedHTML produced by a named policy. That policy is your single audit chokepoint.

// react-lab/src/fallback/trustedTypesPolicy.js
const policy = trustedTypes.createPolicy('app#html', {
  createHTML: (s) => sanitizeToFixedPoint(s),         // F3
  createScriptURL: (u) => allowlistUrl(u),
  createScript: () => { throw new Error('no dynamic script'); },
});

Wiring React through it: React's host config assigns dangerouslySetInnerHTML.__html to innerHTML. Under enforced Trusted Types, that assignment must be a TrustedHTML — so we make React's DOM path (or a shim over it, F4) route through policy.createHTML. Now the "dangerous" hatch is forced through your sanitizer, and a missed sanitize fails closed instead of open.

🧠 Brain Power
Trusted Types closes DOM sinks (Track A5 mechanism 4) categorically. Which sinks does it not cover? (Server-reflected mechanism-1 HTML in the initial document, and markup-driven network from the speculative pipeline — F5's CSP covers those. No single control covers all phases; you layer.)

F3 · Sanitizer API + fallback, mXSS-resistant

Inside createHTML you need a sanitizer that is idempotent under re-serialization — otherwise E6/mXSS defeats you.

// react-lab/src/fallback/sanitize.js  (sketch)
function sanitizeOnce(s) {
  if (window.Sanitizer && Element.prototype.setHTML) {   // native Sanitizer API
    const t = document.createElement('template');
    t.setHTML(s, { sanitizer: SAFE_CONFIG });
    return t.innerHTML;
  }
  return DOMPurify.sanitize(s, PURIFY_CONFIG);              // polyfill
}
function sanitizeToFixedPoint(s, max = 4) {                 // the mXSS fix
  let cur = sanitizeOnce(s);
  for (let i = 0; i < max; i++) {
    const next = sanitizeOnce(cur);
    if (next === cur) return cur;   // reached a fixed point -> stable on reparse
    cur = next;
  }
  return '';                        // didn't converge -> refuse (fail closed)
}

Where to intercept in React: the commit phase (Track D). The sanitize must run at the sink, in the insertion context (Track B5), not once at input — otherwise second-order/context-mismatch bugs slip through.

F4 · Interception architecture (the design decision)

ApproachProsCons
Monkey-patch sinks (wrap Element.prototype setters, Track A2 mixins)framework-agnostic; covers non-React sinks; works with no CSPfragile vs. spec growth; must cover every mixin owner; perf on hot setters
Host-config shim (wrap react-dom's setInitialProperties/commitUpdate)precise; runs exactly at commit; minimal surfaceReact-version-coupled; misses non-React sinks
Trusted Types + policy (browser-enforced)fail-closed; one audit surface; obfuscation-proofChromium-centric today; needs the polyfill/shim elsewhere (this is the "fallback")
Service worker / CSP layercovers network/egress & the speculative phasedoesn't see in-page DOM sinks
The recommended stack (what react-lab implements): Trusted Types where available → its policy runs sanitizeToFixedPoint → a host-config/prototype shim provides the same typed chokepoint as a fallback in non-Chromium browsers and for non-React sinks → strict nonce CSP as the network/speculative backstop. Each layer covers a phase the others can't.

Performance note (commit-phase cost)

The shim runs on every host-prop commit. Keep the fast path free: only HTML/URL/script props hit the sanitizer; everything else is a type-check and pass-through. Measure µs/commit and page-load delta (F6 metrics).

F5 · CSP as defense-in-depth

Content-Security-Policy:
  require-trusted-types-for 'script';
  trusted-types app#html;
  script-src 'nonce-RANDOM' 'strict-dynamic';
  object-src 'none'; base-uri 'none';
  connect-src 'self'; img-src 'self';        <- blunt the speculative-phase exfil (Track C)

The CSP does what the sink shim can't: refuses inline/injected script regardless of spelling (mechanism 1/2), and constrains markup-driven network from the preload scanner (Track C). Add Content-Security-Policy-Report-Only first to find violations without breaking the app.

F6 · The evaluation harness

A defense claim is only credible with a corpus and an oracle. Two pieces, both shipped:

  • Corpus — the 120-payload bank (Module 19) + the mXSS/parser- differential seeds here, tagged by mechanism. react-lab/src/corpus/.
  • Differential oracle — the standalone harness runs parse → serialize → reparse to a fixed point and flags non-idempotent strings and handler regrowth. Also embedded live in the React lab.

📌 The falsifiable claim
State it as an invariant, not a blocklist: "Every value reaching an A5 sink is a policy-produced typed value or a re-serialization fixed point; otherwise the sink throws. Evaluated over corpus C (N payloads) with 0 in-scope bypasses, X% benign compatibility, Y µs/commit." A reviewer refutes it by breaking the invariant, not by finding "one more payload."
