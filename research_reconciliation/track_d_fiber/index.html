React Internals: Fiber & Reconciliation

To defend React you must know the exact line where a string becomes DOM. That line is in the commit phase of the reconciler, inside the react-dom host config. Everything before it is bookkeeping; everything dangerous happens there.

D1 · Element → Fiber

JSX compiles to React.createElement(type, props, ...children), which returns a plain element object (a description, not a node). React turns each element into a fiber — a unit of work:

fiber = {
  type,            // 'div' | FunctionComponent | ...
  pendingProps, memoizedProps,
  stateNode,       // the actual DOM node (for host components)
  child, sibling, return,   // the fiber tree links
  alternate,       // the fiber from the OTHER tree (double buffering)
  flags,           // effect tags: Placement, Update, Deletion, ...
  lanes,           // scheduling priority
}

React keeps two fiber trees: current (on screen) and workInProgress (being built). They point at each other via alternate. This double-buffering is why React can build a whole update off-screen and swap it atomically — and why a security invariant must hold on the WIP tree before commit.

D2 · The reconciliation algorithm

Reconciliation diffs the new element tree against the current fiber tree using two heuristics (O(n) instead of O(n³)):

  1. Different type ⇒ replace subtree. <div> → <span> tears down and rebuilds.
  2. Same type ⇒ keep the node, update props (a "bailout" from recreation). Keys match children across reorderings.

Work happens in two phases: render (beginWork / completeWork build the WIP tree and mark effects — no DOM touched, interruptible) and commit (commitWork applies effects to the DOM — synchronous, not interruptible).

D3 · Concurrent scheduling

Concurrent React can interrupt, pause, and replay the render phase using lanes (priority bitmasks). useTransition, Suspense, and time-slicing all rely on the render phase being pure and restartable.

Security angle: because render can run multiple times before commit, any side-effect or security check you put in render may run 0, 1, or many times — never rely on render-phase effects for a security invariant. The invariant must be enforced at commit (the single, synchronous DOM-mutation point), which is exactly why Track F hooks the host config, not component code. Interruption/replay must not be able to smuggle an unchecked value to commit.

D4 · The DOM host config

react-dom plugs a host config into the reconciler. Its commit-time functions — createInstance, setInitialProperties, updateProperties, commitUpdate — are where props become DOM. Key behaviors:

Host-config behaviorSecurity relevance
attribute vs. property routingReact decides per-prop whether to call setAttribute or assign a DOM property; URL props (href/src) and dangerouslySetInnerHTML take special paths.
dangerouslySetInnerHTMLrouted straight to node.innerHTML with no escaping — the primary sink (Track E1).
event delegation at the rootReact attaches ONE listener per event type at the root and dispatches synthetically; on* props are not inline DOM handlers, which is why JSX onClick is safe — but spread {...props} can still inject a real onerror if it reaches the attribute path (E3).
hydrationon the client, React adopts server-rendered DOM instead of creating it — a different code path with its own risks (D5, E4).

D5 · Server rendering & hydration

renderToString / renderToPipeableStream produce an HTML string on the server; the client then hydrates — attaches fibers/handlers to the existing DOM without recreating it.

  • SSR text/attributes are escaped by React's string renderer — but the same escape-hatch sinks apply (dangerouslySetInnerHTML, URL props).
  • Hydration mismatch: if server and client render different markup, React reconciles the difference; historically, mismatches around raw-HTML/attribute boundaries have produced injection (E5).
  • Embedded state: SSR frameworks serialize data into an inline <script> (__NEXT_DATA__, __INITIAL_STATE__) — a </script>-breakout sink that lives outside React's escaping (E4).
✅ The one sentence to carry into Track E & F
React's escaping happens in the host config at commit for text and most attributes — so every XSS in React is a place where data reaches the DOM bypassing that path: an explicit escape hatch, a special-cased prop, SSR string embedding, or a post-commit mutation. Track F wraps the host config so those paths become typed chokepoints.
