Embedded & Interactive Content

Of all seven categories, these two carry the most security weight. Embedded content pulls in external resources or foreign vocabularies; interactive content is the activation surface. A defender should treat both as "not allowed in untrusted HTML" by default.

⚠️ The big one: embedded content is also phrasing
Because embedded content nests inside phrasing (page 1's Euler diagram), an <img>/<svg> is allowed anywhere text is allowed — including inside a <p>, an <a>, a <span>. So "I only allow inline formatting" does not exclude embedded content unless you say so explicitly. This is a classic sanitizer allowlist mistake: permit phrasing, forget that <svg> is phrasing, and you've allowed a foreign parser with its own <script>.

Interactive content — the activation surface

Content "specifically intended for user interaction": <a> (with href), <button>, <input> (unless hidden), <select>, <textarea>, <details>, <label>, plus media with controls and <img usemap>/<object usemap>.

  • Nesting rule: interactive content generally must not be nested inside other interactive content (no <a> inside an <a>, no <button> inside an <a>) — a conformance rule with real UX/security reasons (ambiguous activation targets).
  • Conditional membership: whether an element is interactive can depend on attributes (<input type=hidden> is not; <video controls> is). Your categorizer marks these with a *.

The defender's rule of thumb

For untrusted/user HTML: allow a phrasing subset + a few flow blocks; deny embedded and interactive content wholesale (no iframe/object/embed/svg/math/canvas, no form controls, and constrain <a href> to safe schemes). Everything dangerous in the main course's mechanism taxonomy lives in these two categories or in <a>'s URL — so excluding them by category is a principled, near-complete filter.
