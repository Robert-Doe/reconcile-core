07

The Big Analogy

Recall Module 06's relay runners, each carrying the baton one leg at a time. This module adds exactly one new rule to the relay: before starting each leg, a runner checks a stopwatch. If time's nearly up, they don't run their leg at all — they set the baton down at the checkpoint they're already standing at and step aside, letting anyone else who's waiting go first. Someone (possibly a different runner entirely) picks the baton back up later and continues from that exact checkpoint.

Nothing about how the relay itself works changed — legs are still run one at a time, the baton still marks "where we are" precisely. The only addition is permission to stop looking at the stopwatch and yield the track.

07

What Happens, Step by Step

Rendering a large tree via renderRootConcurrent:

  1. runChunk() is called (synchronously, the first time).
  2. A fresh shouldYield is created for this chunk (a fresh deadline, or in tests, a fresh counter) — never reused from a previous chunk.
  3. workLoopConcurrent(cursor, shouldYield) runs Module 06's exact loop, but checks shouldYield() before every unit.
  4. The moment shouldYield() returns true, the loop stops and returns whatever fiber it was about to process next — call it the new cursor.
  5. If cursor is null, the whole tree is done. Otherwise, schedule(runChunk) — by default, setTimeout(runChunk, 0) — queues the next chunk and returns, genuinely giving up control.
  6. Whatever else was waiting on the event loop (a click handler, a competing timer, a repaint) gets to run now, before runChunk is called again.

07

The Code, Explained

One added condition

// Module 06:
export function workLoopSync(rootFiber) {
  let next = rootFiber;
  while (next !== null) { next = performUnitOfWork(next); }
  return rootFiber;
}

// Module 07 — the only difference is highlighted:
export function workLoopConcurrent(next, shouldYield) {
  while (next !== null && !shouldYield()) {
    next = performUnitOfWork(next);
  }
  return next;   // null = done; non-null = "resume from here"
}

The factory pattern — and the bug that made it necessary

function runChunk() {
  const shouldYield = createShouldYield();   // FRESH every chunk
  cursor = workLoopConcurrent(cursor, shouldYield);
  if (cursor === null) { onComplete(rootFiber); }
  else { schedule(runChunk); }
}

Verified necessary the hard way — see the "Crazy detail" below.

07

Limits — What You Cannot Do Yet

Can't do yet
  • Prioritize one update over another — every chunk here is treated equally. Real "lanes" (Track 2's A3) let a click handler's update jump ahead of a background data refresh.
  • Actually respond to real user input arriving mid-render and change course — this module proves control returns to the event loop, not that anything interesting happens with that returned control yet.
  • Commit anything — this is still pure tree-building, same as Module 06.
Can do
  • Pause a render at any fiber boundary and resume it correctly later, proven identical to an unyielded run.
  • Demonstrate, with a real competing macrotask (not a metaphor), that the browser genuinely gets a turn mid-render.
  • Explain exactly why a shared, stateful shouldYield across chunks is a real, not hypothetical, bug.

Getting a blank or broken result — or a script that never finishes?

If node verify.mjs appears to hang, the near-certain cause (this course hit it directly) is a shouldYield being shared across chunks instead of recreated per chunk via createShouldYield — a counter or deadline that's already tripped makes every subsequent chunk do zero work and yield instantly, forever. Kill the process and check that every call site passes a factory, not a bare function.

Crazy detail — this course's own hang, and how it was found

The first draft of verify.mjs's Test 2 hung indefinitely — this exact document you're reading was blocked on a real Node process that had to be located (via a process list) and force-killed before the bug could be fixed. The cause: a single shouldYield closure, a call counter, was reused across every chunk instead of recreated per chunk. Chunk 1 legitimately did 2 units of work and yielded on its 3rd check. Chunk 2 resumed with the same, already-tripped counter — which immediately returned true again, before doing any work at all. Every chunk after that did the same: check, yield instantly, reschedule, forever. The fix was the createShouldYield factory now in the source. This is, unplanned, the single clearest real-world argument for why real React's Scheduler recomputes a fresh deadline every callback rather than checking one deadline computed once at the start of the whole render.

Brain Exercise

Before reading on: if schedule were changed from setTimeout(cb, 0) to calling cb() directly, synchronously (no macrotask at all), would workLoopConcurrent's pause-and-resume logic still be "correct" in the sense Test 1 checks? Would Test 2 still pass?

Work it out, then check

Test 1 would still pass — the tree-correctness proof never depended on when chunks run relative to anything else, only that resuming from the returned cursor eventually reaches null and matches the unyielded tree. Test 2 would fail: calling cb() directly, synchronously, never actually returns control to the event loop between chunks — it's just a recursive function call wearing a "chunk" costume. The competing setTimeout task would never get a chance to run until the entire (synchronous, if reframed this way) render finished, exactly like Module 06's blocking workLoopSync. This is the precise, testable difference between "the code is organized into chunks" and "the browser actually gets a turn" — and it's why this module's `schedule` default specifically has to go through a real macrotask API.

07

There Are No Dumb Questions

Why setTimeout and not requestIdleCallback, which sounds more purpose-built for this?

requestIdleCallback isn't available in Node (this module's test environment) and has inconsistent browser support/timing characteristics that real React's team explicitly moved away from for exactly that reason — real Scheduler uses MessageChannel instead, for both of those reasons (universal availability, consistent firing). setTimeout(fn, 0) is the simplest option that's both real (a genuine macrotask) and available everywhere, which is why this module uses it as the default while documenting the real mechanism (Track 2 A3) separately.

Does yielding mean React "checks for user input" during the gap?

Not directly — yielding means control returns to the browser's event loop, and the event loop is what decides what runs next (a click handler, a timer, a repaint, anything queued). React doesn't poll for input; it simply stops holding the thread hostage long enough for whatever's already queued to get a turn. Module 07's proof (a competing setTimeout) demonstrates exactly this queued-callback mechanism, which is the same mechanism a real click handler waiting in the queue would benefit from.

If a render is paused and never resumed, is anything left in a bad state?

No — this is exactly Module 05's double-buffering guarantee doing its job. Everything this loop has built so far lives on the workInProgress side; current was never touched. An abandoned render just becomes garbage-collectable state that nothing ever pointed a "real" tree pointer at.

Is 14 chunks for a 27-node tree realistic for real React?

No — that number is an artifact of this module's deliberately aggressive test mock (yield after 2 units, to force many chunks deterministically without relying on wall-clock timing). Real React's actual default time budget is on the order of 5ms per chunk, which on ordinary hardware processes far more than 2 fiber updates before yielding. The "informational" run in verify.mjs, using a real performance.now()-based deadline, produces a different (and machine-dependent) chunk count — logged but deliberately not part of the graded assertions, for exactly that reason.

What's Next

The loop can now build a tree from nothing, in pausable chunks. But every render so far has started from a bare, childless fiber — nothing here has ever compared "what's new" against "what was there last time." Module 08 introduces the first real diffing decision: when a fiber's type hasn't changed, update it in place instead of throwing it away — the single-child fast path that's the seed of every later reconciliation rule.
