Module 04Mount — Element Tree to Fiber Tree

Module 01-02 build elements. Module 03 hand-wires fibers. This module writes the one function that connects them: give it an element, it gives back a fully-linked fiber tree — including calling every function component along the way to find out what it actually renders.

The whole claim, once — everything else is consequence

A function-component fiber has exactly one child: the fiber for whatever the function returned when called. Mounting isn't "convert this element to a fiber" — it's "convert this element to a fiber, and if that required calling a function, keep going with whatever came back."

04

The Big Analogy

Back to the furniture shop. A customer's work order says "type: Custom Bookshelf Kit." That's not a real, physical thing you can hand a carpenter — it's a recipe, and the only way to find out what it actually contains is to open it: unwrap the kit, and inside is another work order, this one for "type: wooden frame with 4 shelves," which is a real buildable thing.

Mounting is the clerk unwrapping every kit-type order they receive, all the way down, until every remaining order is for a real, physical thing. The "Custom Bookshelf Kit" ticket still exists in the shop's paperwork — it's just that its one and only attached sub-ticket is "wooden frame," because that's what was inside.

04

What Happens, Step by Step

Mounting createElement(Card, { title: 'Hello', showFooter: false }), where Card returns a div containing an h1, a text string, and a conditional footer:

  1. Create a fiber for the Card element. type is a function, so tag = FunctionComponent.
  2. Because it's a FunctionComponent: call Card(props). It returns a new element (the div).
  3. Mount that element, and set the result as the Card fiber's child.
  4. The div's type is a string, so tag = HostComponent. Its children come from props.children: [<h1>, "plain text child", false] (the last one because showFooter was false).
  5. normalizeChildren flattens and filters that array: false is dropped entirely. Two children remain: the h1 element and the string.
  6. Each remaining child is mounted and linked via appendChild (Module 03) — the string becomes a HostText fiber directly, no further recursion needed.

A Map of the State

Input element (nested, via createElement)

Card { title: "Hello", showFooter: false }
└─ div { className: "card" }
   ├─ h1 → "Hello"
   ├─ "plain text child"
   └─ false          ← showFooter && <footer/>

Output fiber tree (mount() result)

FunctionComponent(Card)
└─ HostComponent(div)
   ├─ HostComponent(h1)
   │  └─ HostText("Hello")
   └─ HostText("plain text child")
      ← footer produced NO fiber at all
Watch it

There is no third child under div representing the dropped footer — not a placeholder, not a fiber marked "empty." normalizeChildren filters it out before any fiber for it is ever created. This is verified, not assumed: verify.mjs's traversal has exactly 5 entries, and independently asserts "div has exactly 2 children."

04

The Code, Explained

The FunctionComponent branch — the heart of the module

if (fiber.tag === FunctionComponent) {
  const rendered = fiber.type(fiber.pendingProps);   // CALL it
  const childFiber = mount(rendered);                // mount what it returned
  appendChild(fiber, childFiber);
  return fiber;
}

Verified structurally against real React's updateFunctionComponent (react-dom.development.js:19585), which calls renderWithHooks(...) to get nextChildren — the function's return value — before doing anything else with this fiber. The function component fiber itself never has "real" children of its own; it has exactly one child, which is whatever its function call produced.

Dropping falsy children — where {cond && <X/>} actually gets handled

function visit(child) {
  if (child === null || child === undefined || typeof child === 'boolean') return;
  if (Array.isArray(child)) { for (const c of child) visit(c); return; }
  out.push(child);
}

Exactly three values are silently dropped: null, undefined, boolean. Not 0. Not ''. This is a real, well-documented React footgun — {count && <Badge/>} renders a visible, stray "0" text node when count is 0, because 0 is a number, not a boolean, and this function only drops booleans.

04

Limits — What You Cannot Do Yet

Can't do yet
  • Re-mount on top of an existing tree ("update") — every call to mount() builds a brand new tree from nothing. There's no "last time" yet.
  • Pause partway through — mount() is recursive; like any recursive function, it runs to completion or not at all.
  • Touch a real DOM node — stateNode stays null on every fiber this module produces.
Can do
  • Turn any element tree — including ones with function components, conditionals, and text — into a correctly-shaped fiber tree.
  • Predict, correctly, which children of a JSX expression disappear entirely versus render as visible (if unexpected) text.
  • Explain exactly why a function component's fiber has one child, never "its own" children.

Getting a blank or broken result?

A TypeError: fiber.type is not a function almost always means an element's type was a string (like 'div') but got routed into the FunctionComponent branch — double check the tag assignment logic in createFiberFromElement if you've modified it. If the footer shows up anyway, confirm you're testing with showFooter: false (a boolean), not showFooter: 0 or "" — only true booleans get dropped, on purpose.

Brain Exercise

Before reading on: if Card's function body itself contained a nested function component — say, Card returns <Wrapper><div/></Wrapper> — how many FunctionComponent-tagged fibers appear in the mounted tree, and how are they related?

Work it out, then check

Two: one for Card, one for Wrapper — and Wrapper's fiber is Card's fiber's child, exactly as if Wrapper were a host element. mount() doesn't special-case "a function component that returns another function component" — it's the exact same recursive call, one level deeper. This is precisely why the recursion in this module has to eventually become the explicit loop in Module 06: nothing bounds how many function components can be nested this way, and a sufficiently deep chain would exhaust the call stack in a way an explicit loop over a heap-allocated fiber tree never would.

04

There Are No Dumb Questions

Why does a FunctionComponent fiber exist at all, if it just has one child that's "the real thing"? Why not skip straight to mounting the returned element?

Because the component's identity has to persist across renders for exactly the reason Module 03 introduced pendingProps/memoizedProps: on the next render, this course needs somewhere to store "here's the props Card was called with last time" so Module 10's bailout can compare them. If we skipped straight to the div, there'd be no fiber anywhere remembering that a Card call happened at all — and Module 13's hooks explicitly need a fiber "home" for state, which must be the component's own fiber, not its rendered output's.

What happens if a function component returns an array of elements (not wrapped in a single parent)?

This module's mount() doesn't handle that case — it calls mount(rendered) expecting one element, string, or number. Real React supports returning arrays/fragments via additional reconciliation logic this course doesn't build (documented out of scope). If you tried it here, isElement() would return false for a plain array and the function would throw — a deliberate, honest failure rather than silent wrong behavior.

Is `normalizeChildren` doing anything React-specific, or is it just `Array.flat()` plus a filter?

Structurally it's extremely close to flatten-plus-filter — the React-specific part is entirely the *choice* of which three values count as "nothing": `null`, `undefined`, `boolean`. `Array.prototype.flat()` alone has no concept of that; we wrote the recursive `visit` by hand specifically so those three exact values are dropped and nothing else is.

Why is `createFiberFromElement` a private, unexported function here, when Module 03 exports `createFiber`?

Different jobs: Module 03's `createFiber` is a bare constructor call useful on its own (you used it directly in that module's `verify.mjs`, hand-wiring a tree). This module's element-to-one-fiber step only makes sense embedded inside the larger recursive `mount()` traversal — nothing else in this course calls it in isolation, so exporting it would just be unused surface area (see DECISIONS.md).
