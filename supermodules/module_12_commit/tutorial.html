Module 12The Commit — Real DOM Calls

Every module since 01 has been building toward one moment: real appendChild. This module is that moment — a fiber tree built entirely off-screen, then attached to a real, visible document with the fewest possible real DOM calls.

The whole claim, once — everything else is consequence

New DOM nodes are built and nested entirely off-screen during completion (bottom-up); only the OUTERMOST new fiber in a subtree needs an explicit Placement flag, because everything inside it arrives already attached, for free.

The Big Analogy

A furniture delivery crew doesn't carry a sofa into the house cushion by cushion, then the frame, then the legs, assembling it in your living room. They build the whole sofa in the truck — frame, cushions, legs, all attached to each other — and then make exactly ONE trip through your front door with the entire finished piece. Every other room in the house is untouched, because nothing else needed delivering.

This module's tree-building (Module 04/06) is the truck. appendAllChildren is assembling the sofa inside it, off the street, where nobody watching your house sees anything change yet. commitPlacement is the one trip through the door.

What Happens, Step by Step

Mounting <Card title="Hello"> (a div containing an h1 and a text node):

  1. completeAllWork walks the fiber tree bottom-up (children before parents — Module 06's completion order).
  2. The text fiber completes first: document.createTextNode("Hello"). Detached — attached to nothing yet.
  3. The h1 fiber completes: document.createElement('h1'), then appendAllChildren puts the text node inside it. The h1 now contains real text, but is itself attached to nothing.
  4. The div fiber completes the same way — createElement('div'), then the h1 AND the other text fiber both get appended inside it, off-screen.
  5. Only the Card fiber (the outermost NEW thing) has flags |= Placement. Everything below it does not.
  6. collectEffects (Module 11) finds exactly one fiber with `Placement`: Card.
  7. commitPlacement(Card) — Card isn't a host node, so it recurses into its child (div) — which IS host — and does exactly one real appendChild(divInstance) into the live container. The h1 and both text nodes arrive as part of that single call, already inside div.

The Code, Explained

Building off-screen, verified against real React's exact traversal

function appendAllChildren(parent, workInProgress) {
  let node = workInProgress.child;
  while (node !== null) {
    if (node.tag === HostComponent || node.tag === HostText) {
      parent.appendChild(node.stateNode);        // off-screen — parent isn't attached yet
    } else if (node.child !== null) {
      node.child.return = node; node = node.child; continue;
    }
    if (node === workInProgress) return;
    while (node.sibling === null) {
      if (node.return === null || node.return === workInProgress) return;
      node = node.return;
    }
    node.sibling.return = node.return; node = node.sibling;
  }
}

Transcribed directly from real React's actual function of the same name (line-cited in DECISIONS.md) — the same non-recursive, return-pointer-patching shape as Module 06's work loop, now walking a completed subtree instead of building one.

Updates never call commitPlacement at all

// completeDomWork's HostText branch:
if (fiber.stateNode === null) {
  fiber.stateNode = document.createTextNode(fiber.pendingProps);   // mount
} else if (oldText !== fiber.pendingProps) {
  fiber.stateNode.textContent = fiber.pendingProps;                // update — SAME node, mutated
}

Verified by verify.mjs's Proof 2: wipTextFiber.stateNode === attachedNode is true — the update never allocates a new text node, and never goes anywhere near commitPlacement, because it was never flagged Placement in the first place.

Brain Exercise

Before reading on: if a component's ENTIRE returned subtree is brand new (a full mount, not an update), does every single host fiber inside it need its own Placement flag, or just the outermost one?

Work it out, then check

Just the outermost one — this module's own Proof 1 demonstrates it directly: only cardFiber (a non-host FunctionComponent) carries Placement; the div, h1, and both text fibers inside it carry none. Because appendAllChildren already assembled all of them into the div's real DOM instance off-screen during completion, a single commitPlacement call on the outermost fiber — which recurses down to find the first HOST descendant and inserts THAT — brings the entire already-assembled subtree along in one real DOM operation. Flagging every descendant individually would mean redundant, unnecessary calls for something that's already structurally attached to its parent.

There Are No Dumb Questions

Why build the DOM off-screen at all — why not just attach each node the instant it's created?

Two real reasons: first, attaching nodes one at a time to a live document can trigger layout/reflow work in a real browser repeatedly, whereas building off-screen and attaching once triggers it only once. Second — and more fundamental to this course — off-screen building can be safely ABANDONED mid-way (Module 07's interruptible rendering) without the user ever seeing a half-built tree flash on screen, because nothing about it was ever visible in the first place.

Does `getHostSibling` matter for a fresh mount, or only for updates/reorders?

Mostly the latter — on a fresh mount into an empty container, there's usually nothing to insert before (the result is `null`, meaning "just append"). It becomes essential once Module 09's moves are involved: inserting a moved item at the correct position among already-committed siblings requires knowing exactly which real DOM node to `insertBefore`, and that's precisely what `getHostSibling` computes by walking the fiber tree, not the real DOM.

What happens to a deleted fiber's real DOM node — does `commitDeletions` also detach its children individually?

No — `removeHostDescendants` finds the outermost host node(s) within a deleted fiber and calls `removeChild` on those alone. Removing a parent DOM node from the document also removes everything nested inside it automatically (that's how the DOM works) — so, symmetrically with placement, only the outermost real node(s) need an explicit removal call.

Is `className` really special-cased in real react-dom, or is that this course's own invention?

Real: `class` is a reserved word in JavaScript, so DOM elements expose it as the `className` property instead of a `class` property — real `react-dom`'s actual host config has to special-case this exact mismatch between the JSX prop name authors write (`className`, matching the DOM property) and what ends up as the HTML attribute (`class`). This module's `setInitialProperties` reproduces that one specific, real special case; it isn't inventing new behavior.
