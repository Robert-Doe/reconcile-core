Module 08The Single-Child Fast Path

Every module so far has only ever mounted from nothing. This is the first module where there's a "last time" to compare against — and the first real reconciliation decision: reuse the old fiber, or throw it away?

The whole claim, once — everything else is consequence

Same key and same type → reuse the fiber (via Module 05's double buffering) and just give it new props. Anything else → delete the old one, build fresh. The decision is made once, per position, before anything else happens.

08

The Big Analogy

A hotel room between guests. Housekeeping's decision isn't "burn the room down and rebuild it" every checkout — it's "is the next guest's booking compatible with what's already installed?" A returning guest with the same room type gets the same physical room, freshly made up: same bed frame, same furniture, new sheets. A guest who booked a fundamentally different room type (a suite instead of a single) doesn't get the old room adapted — that room gets marked for a totally different renovation, and the guest gets an entirely different physical room.

The bed frame (the fiber object) either survives, refreshed, or it doesn't. There's no in-between where half the frame is old and half is new — the decision is made once, at check-in, before any sheets are changed.

08

What Happens, Step by Step

reconcileSingleChild(parent, oldChild, newElement):

  1. Compare oldChild.key to newElement.key. Different → this specific old child is marked for deletion; if there's a next sibling, check IT next (a later sibling might still match).
  2. Keys match → compare oldChild.type to newElement.type.
  3. Types match: mark any of oldChild's remaining siblings for deletion (a single-child slot keeps exactly one survivor), then clone oldChild via createWorkInProgress with the new props, reset index/sibling, return it.
  4. Types don't match: mark oldChild and all its remaining siblings for deletion, stop searching, fall through to step 5.
  5. No match survived the search (or none existed): create a brand new fiber for newElement, unconnected to anything from before.

A Map of the State

Different type — REPLACE

result.type                     "span"
result.alternate                 null   ← brand new
parent.deletions                [oldChild]
Brain power

In the REUSE case, oldChild.memoizedProps.className is still "old" after the call — the fiber that's now "current" (from the last completed render) is completely untouched. Only the new, pooled object (result, oldChild.alternate) got the new props. This is Module 05's guarantee, still holding, one module later.

The Code, Explained

The decision, verified against real React's actual function

if (child.key === key) {
  const sameType = isText ? child.tag === HostText : child.type === newType;
  if (sameType) {
    deleteRemainingChildren(returnFiber, child.sibling);
    const existing = useFiber(child, props);   // ← Module 05's createWorkInProgress
    existing.return = returnFiber;
    return existing;
  }
  deleteRemainingChildren(returnFiber, child);  // key matched, type didn't: all of it goes
  break;
} else {
  deleteChild(returnFiber, child);              // wrong key: just this one, keep looking
  child = child.sibling;
}

Verified against real reconcileSingleElement (line-cited in DECISIONS.md) — same branch structure, same which-deletion-call-gets-which-argument logic.

useFiber is Module 05, plus two resets

function useFiber(fiber, pendingProps) {
  const clone = createWorkInProgress(fiber, pendingProps);   // Module 05, unmodified
  clone.index = 0;
  clone.sibling = null;
  return clone;
}

Real React's own source comment, quoted directly: "We currently set sibling to null and index to 0 here because it is easy to forget to do before returning it." A reused fiber must not carry forward tree-shape data from a context where it might have had different siblings.

Limits — What You Cannot Do Yet

Can't do yet
  • Reconcile a whole array of children against a whole old array — this module only handles one position (Module 09's job).
  • Actually remove anything from the DOM — deletions is a list of intentions, not an action.
  • Decide "skip this subtree entirely" based on props being unchanged — that's Module 10's bailout, a step beyond just "reuse the fiber."
Can do
  • Correctly decide reuse-vs-replace for one child position, matching real React's actual algorithm.
  • Explain exactly why keys are checked before types, and why a type change discards the ENTIRE remaining old sibling chain, not just the mismatched fiber.
  • Predict, for any before/after pair, whether a fiber survives an update or gets replaced.

Brain Exercise

Before reading on: an old child has key="row-1", type 'div'. A new element arrives with key="row-1", type 'span'. Is the old fiber's props relevant to this decision at all?

Work it out, then check

No — not even slightly. The type mismatch alone is fully decisive; reconcileSingleChild never inspects child.pendingProps or child.memoizedProps when comparing key and type. Two elements can have wildly different props and still reuse the same fiber (Scenario 1 changes className from "old" to "new" and still reuses); two elements can have identical props and still get a brand-new fiber, if their types differ. This is worth sitting with: "did the props change?" is an entirely separate question from "should this fiber survive?", and this module only ever answers the second one.

08

There Are No Dumb Questions

Why check key before type? Wouldn't checking type first catch more "obviously the same" cases?

Because key is the author's explicit statement of identity — "this is logically the same item as last time," independent of what it renders as — while type is more like an implementation detail of that item. A key mismatch means "this is a conceptually different thing," full stop, regardless of whether the types happen to coincidentally match. Checking type first would risk reusing a fiber for a genuinely different logical item just because it happened to render the same tag — exactly the kind of bug keys exist to prevent (foreshadowing Module 09).

What does "single-child" mean here — does this only apply to components with exactly one child in their JSX?

It means this specific function is only reconciling ONE position (a component's single returned element, or one array slot in isolation) against ONE old fiber. Module 09 is where an entire array of children gets reconciled against an entire array of old children, using a related but more elaborate algorithm — this module is the piece Module 09 builds on, not a separate case for "components that happen to return only one thing."

If the type matches but I don't reset `index`/`sibling`, what actually breaks — concretely?

Say the reused fiber previously had a sibling from a time it wasn't the only child. If `sibling` isn't reset to `null`, `forEachFiber` (Module 03) would walk into that stale sibling — a fiber that no longer has any relationship to this render at all — producing a corrupted traversal that visits nodes that aren't really part of the current tree. Resetting is what keeps "this fiber's own history" from leaking into "this fiber's current tree-shape."

Does `deleteChild`/`deleteRemainingChildren` free any memory or detach anything right now?

No — they only push a reference onto `returnFiber.deletions`. The fiber being "deleted" still exists, still has all its fields, and is still reachable via that array. Nothing about the actual tree structure or the real DOM changes until Module 11 turns this list into real removal work during the commit phase.
