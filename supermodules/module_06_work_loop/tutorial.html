Module 06The Unit-of-Work Loop

Module 04's mount() works, but it's recursive — it can't be paused, because pausing a recursive call means pausing the JS call stack itself, which you don't control. This module rebuilds the exact same tree using nothing but an explicit "what's next" pointer, and proves — by tracing both — that the result is identical.

The whole claim, once — everything else is consequence

beginWork does one fiber's work, one level of children, never recursing. The loop calling it repeatedly is what provides depth — not the call stack. Stack depth stays constant no matter how deep the tree is.

The Big Analogy

Module 04's mount() was a single courier who takes an entire package to its final destination in one uninterrupted trip, however many stops that takes — no matter how far, they don't come back to base until it's fully delivered. Module 06 replaces that courier with a relay: one runner goes exactly one leg, hands off a baton (a fiber reference) at a checkpoint, and steps aside. The next runner picks up the baton and runs the next leg. Nobody runs the whole route in one uninterrupted trip.

The destination reached is identical either way. What's different is that the relay can be paused between any two legs — the baton just sits at a checkpoint until someone picks it up again — while the single-courier version can only be paused by the courier themselves choosing to stop mid-stride, which recursive function calls in JS simply cannot do.

06

What Happens, Step by Step

workLoopSync(rootFiber), for the tree Card → div → [h1 → "Hi", "plain text", footer → "footer text"]:

  1. next = rootFiber (the Card fiber).
  2. Step 1: performUnitOfWork(Card) → beginWork calls the Card function, creates one child fiber (div), links it, returns it. next = div.
  3. Step 2: performUnitOfWork(div) → beginWork creates fibers for all three of div's children (h1, text, footer) as siblings, returns the first (h1). next = h1.
  4. Step 3: performUnitOfWork(h1) → creates its one text child, returns it. next = "Hi".
  5. Step 4: performUnitOfWork("Hi") → HostText, no children, beginWork returns null. completeUnitOfWork checks "Hi"'s sibling — none (it's h1's only child) — goes up to h1, checks h1's sibling — the plain-text fiber. next = "plain text child".
  6. ...and so on, until every fiber has been visited exactly once and completeUnitOfWork walks all the way back up past the root, returning null.

The Code, Explained

beginWork — exactly one level, never more

export function beginWork(fiber) {
  if (fiber.tag === HostText) return null;

  if (fiber.tag === FunctionComponent) {
    const rendered = fiber.type(fiber.pendingProps);
    const child = createFiberForValue(rendered);
    appendChild(fiber, child);
    return fiber.child;                    // ONE child. Not its grandchildren.
  }

  const children = normalizeChildren(fiber.pendingProps.children);
  for (const child of children) {
    appendChild(fiber, createFiberForValue(child));  // siblings, not descended into
  }
  return fiber.child;
}

Compare this to Module 04's mount(), which called mount(child) recursively right here. This version calls createFiberForValue(child) — no recursive call to beginWork anywhere. The loop (not this function) is what eventually visits each new child and goes one level deeper, on a later iteration.

completeUnitOfWork — sibling, then parent, repeat

export function completeUnitOfWork(unitOfWork) {
  let completedWork = unitOfWork;
  do {
    const returnFiber = completedWork.return;
    const siblingFiber = completedWork.sibling;
    if (siblingFiber !== null) return siblingFiber;
    completedWork = returnFiber;
  } while (completedWork !== null);
  return null;
}

Verified structurally against real React's identically-named function (line-cited in DECISIONS.md) — same sibling-first, then-go-up-and-repeat shape.

Limits — What You Cannot Do Yet

Can't do yet
  • Actually stop the loop early — workLoopSync runs to completion, just like mount() did. The capability to stop exists now (constant stack depth); the code that uses it doesn't yet.
  • Update an existing tree — every run here still starts from a bare, childless fiber, exactly like a fresh mount.
  • Do anything to the real DOM.
Can do
  • Produce a fiber tree, proven identical to the recursive version, using an explicit loop instead of the call stack.
  • Point to the exact fiber the loop is "at" right now, at any moment, as a plain value — not something buried in stack frames.
  • Explain precisely why beginWork alone could never accidentally become recursive by accident — it structurally never calls itself, only createFiberForValue (which also never recurses).

Brain Exercise

Before reading on: at the moment performUnitOfWork is called for the footer fiber (step 5 in the map above), what is the JavaScript call stack's depth, measured from workLoopSync? And how does that number change if the tree were 100 levels deep instead of 3?

Work it out, then check

The stack is workLoopSync → performUnitOfWork → beginWork (or → completeUnitOfWork) — a small, fixed number of frames, regardless of which fiber is being visited or how deep it sits in the tree. Make the tree 100 levels deep and the stack depth at any given moment is still that same small fixed number — because getting from level 1 to level 100 happened via 100 iterations of the while loop in workLoopSync, not via 100 nested function calls. This is the entire property Module 07 needs: the cost of "how deep is the tree" has been moved from stack frames (which you can't inspect or pause mid-way) to loop iterations (which you very much can).

06

There Are No Dumb Questions

If the tree traversal is identical either way, what did we actually gain by rewriting mount() as a loop?

Nothing observable yet — and that's the point of doing it in its own module, verified against the old version, before adding anything new. Module 07 is where the gain becomes real: it adds exactly one thing (a deadline check and an early return) to this loop, and that one addition is only possible because stack depth here never grows with tree depth. Trying to add the same pause to Module 04's recursive `mount()` would require pausing a JS function mid-call, which isn't something JS lets you do.

Why does `beginWork` create ALL of a host component's children at once, rather than one at a time?

Because siblings need to be linked to each other (`child.sibling = nextChild`) before the loop can discover them one by one — that linking has to happen somewhere, and doing it all at once, right when their parent is visited, is simpler than spreading it across multiple loop iterations. What `beginWork` does NOT do is descend into any of those children's *own* children — that's deferred to when the loop visits each child in a later iteration. "All immediate children, zero grandchildren" is the exact boundary.

Real React keeps `workInProgress` as a variable outside any function. Doesn't that make testing harder — how did you avoid it?

By making `performUnitOfWork` return the next fiber instead of assigning it to a shared variable — see DECISIONS.md. It's a deliberate, documented divergence, not an oversight: real React's module-level variable lets *any* function in its reconciler (there are many, across several files) resume from wherever rendering left off without a value being threaded through every call site. This course doesn't have that many call sites, so an explicit returned value is simpler to read, test, and (in Module 07) hold onto between yields.

Could this loop get stuck forever on a malformed tree?

Only if `completeUnitOfWork`'s `do...while` never reaches a fiber with `return === null` — which would mean a cycle exists in the tree (a fiber whose ancestor chain loops back on itself), which nothing in Modules 03-06 can currently construct. `verify.mjs`'s manual trace includes a 20-iteration safety cutoff specifically as a test-code guard, not because the algorithm itself is expected to loop — a real infinite loop there would indicate a bug in tree construction, not an inherent risk of the traversal algorithm.

What's Next

The loop's stack depth is now constant, independent of tree depth — the one precondition Module 07 needed. Module 07 adds exactly one new idea on top of this exact loop: check a deadline before continuing, and if it's passed, stop and hand control back to the browser (see P6) — resuming later from precisely the next value this loop already tracks.
