Module 09Keyed List Diffing

This is the module the whole "why do keys matter" conversation is actually about. Real React does not run a Longest-Increasing-Subsequence diff on your lists — by its own source comment, it can't, because fibers have no back-pointers. What it runs instead is a cheaper heuristic, and this module reproduces it exactly, including the case where it visibly isn't optimal.

The whole claim, once — everything else is consequence

A single forward pass tracks the highest old index placed so far. A reused item below that mark gets flagged as moved; one at or above it doesn't. This is a running maximum, not a full reorder computation — cheap, and, as this module proves, not always minimal.

09

The Big Analogy

Picture people re-forming a queue after being told the new order. An official walks the new line front to back with one number in their head: "the highest position-tag I've confirmed so far." Person by person: if this person's OLD position-tag is higher than that running number, wave them through — "you were already further back than everyone I've confirmed, you can stay." If their old tag is LOWER than the running number, that's a problem — someone I already confirmed was standing further back than you used to be, so for you to be here now, you must have physically walked forward past them. Tag you for a real move.

The official never looks at the whole line at once, never asks "what's the true minimum number of people who need to move." They make one pass, with one running number, and that's it — fast, but not always the fewest possible taps on the shoulder.

09

What Happens, Step by Step

reconcileChildrenArray(parent, oldFirstChild, newChildren):

  1. Phase 1 (lockstep): walk old and new children together, position by position, as long as keys match. Reuse (same key + type) or replace (same key, different type) at each step. The instant a key doesn't match at the current position, stop — even if it would have matched further along.
  2. If every new child got consumed in phase 1: delete whatever's left of the old chain. Done.
  3. Else if the old chain ran out first: every remaining new child is a fresh insertion — no lookup needed, fast path.
  4. Else (both sides have leftovers that didn't line up): build a Map from the remaining old fibers, keyed by key (or index, if keyless). Look each remaining new child up in it.
  5. For every fiber placed (in either phase), run placeChild: track whether its OLD index is below the running "highest old index seen" — if so, flag it moved; either way, possibly raise the running mark.
  6. Anything still left in the map after the loop was never claimed — delete it.
09

A Map of the State — the famous case

Old order [A, B, C] → new order [C, A, B]. C genuinely moved from last to first; A and B didn't move relative to each other at all.

What actually changed (intuitively)

A(0) B(1) C(2)     ← old
C(2) A(0) B(1)     ← new
      only C moved

What the algorithm actually flags

C: stays  (becomes the mark: 2)
A: MOVED  (old index 0 < mark 2)
B: MOVED  (old index 1 < mark 2)
Crazy detail — real, verified, and counter-intuitive

verify.mjs's Scenario 4, real executed output: movedKeys → ["A", "B"]. Not ["C"]. The item that visually moved is the one NOT flagged; the two that stayed put relative to each other ARE flagged. This is exactly the real, shipping behavior behind a commonly-reported "why did my whole list re-render when I only moved one item" question — reproduced here, not just described.

09

The Code, Explained

placeChild — the entire "did this move" decision, in one function

function placeChild(newFiber, lastPlacedIndex, newIndex) {
  newFiber.index = newIndex;
  const current = newFiber.alternate;
  if (current !== null) {
    const oldIndex = current.index;
    if (oldIndex < lastPlacedIndex) {
      newFiber.flags |= Placement;   // moved backward past something already placed
      return lastPlacedIndex;
    }
    return oldIndex;                 // stays — raises the mark
  }
  newFiber.flags |= Placement;       // brand new — always an insertion
  return lastPlacedIndex;
}

Verified byte-for-byte against real React's actual function of the same name (line-cited in DECISIONS.md). Three cases, no more: reused-and-in-order, reused-and-out-of-order, and brand-new.

Why phase 1 bails on the FIRST mismatch, not the best one

for (; oldFiber !== null && newIdx < newChildren.length; newIdx++) {
  if (oldFiber.index > newIdx) break;
  if (keyOf(newChildren[newIdx]) !== oldFiber.key) break;   // ← stop here, don't look ahead
  ...
}

This trades thoroughness for speed on the common case (nothing reordered): most updates never reach the Map phase at all. The cost of that trade is exactly Scenario 4 — a rearrangement that phase 1 can't resolve gets pushed into the map phase, where the high-water-mark heuristic, not a true minimal-moves computation, takes over.

Limits — What You Cannot Do Yet

Can't do yet
  • Guarantee a minimal number of moves — Scenario 4 is direct proof this algorithm doesn't try to.
  • Actually move anything in a real DOM — Placement is a flag recorded now, acted on in Module 12.
  • Handle portals, fragments, or nested arrays as children — out of scope, matching this course's stated boundaries.
Can do
  • Reconcile an entire keyed array against its previous version, matching real React's actual output for insert/remove/reorder cases.
  • Predict, for any before/after pair of keyed lists, exactly which items get flagged Placement — including the non-obvious cases.
  • Explain precisely why keys are not optional once a list can reorder — Module 01's key-coercion and this module's Map lookup are the same mechanism, now load-bearing.

Getting a blank or broken result?

If Scenario 1 (no change) shows anything in movedKeys, double-check placeChild's comparison direction — it should be oldIndex < lastPlacedIndex, not <=; using <= would wrongly flag every item as moved even when nothing changed, since each item's old index equals the mark right after it's placed.

09

Brain Exercise

Before reading on: old order [A, B, C, D], new order [B, C, D, A] — A moved from front to back, B/C/D shifted forward but kept their relative order. Which items get flagged Placement?

Work it out, then check

Only A. Trace it: B is placed first (new position 0) — old index 1, mark starts at 0, 1 is not < 0, so B stays and raises the mark to 1. C placed next — old index 2, not < 1, stays, mark→2. D placed — old index 3, not < 2, stays, mark→3. Finally A — old index 0, and 0 is < 3 — flagged. This is the mirror image of Scenario 4: moving one item from the front to the back is cheap under this heuristic (only that one item is flagged), while moving one item from the back to the front is expensive (everything else gets flagged). That asymmetry is a direct, provable consequence of scanning in a single fixed direction with a running maximum — not a coincidence, and not something either scenario's outcome could have avoided while keeping the algorithm a single forward pass.

09

There Are No Dumb Questions

Why doesn't real React just fix this with a proper LIS algorithm? It's a well-known technique.

Per the real source comment quoted in DECISIONS.md, the stated reason is structural: fibers only have forward pointers (child/sibling/return — no previousSibling), which rules out the two-ended search a more thorough diff would want, and the team's own assessment was that optimizing further wasn't worth the added complexity for how rarely large reorders happen in practice relative to appends/removes/small in-place updates.

Does using an index as a fallback key (when an item has no explicit key) fix the reordering problem?

No — it actively defeats the entire point of keys. An index-based "key" changes meaning every time the list's order changes (the item now at index 0 might be a totally different logical item than whatever was at index 0 last render), so updateFromMap's lookup-by-index will confidently "match" the wrong item to the wrong fiber whenever a reorder happens. This is why React warns about array-index keys specifically for lists that can reorder — the warning is describing exactly this module's map-phase lookup silently mismatching.

In Scenario 3 (removing B from the middle), why didn't A or C get flagged, even though C's position number changed from 2 to 1?

Because placeChild compares OLD index against the running mark, never new index against old index directly. C's old index was 2; when it's placed, the mark is still 0 (only A had been placed, and A's old index 0 wasn't below the mark either). 2 is not less than 0, so C stays. The DOM position it ends up in is a consequence of B's fiber simply no longer being in the sibling chain — nothing had to "move" C for that to happen once B disappears.

What happens if two children have the same explicit key?

This module's Map-based lookup (existingChildren.set(key, fiber)) means the second occurrence silently overwrites the first in the map — real React detects and warns about this exact situation (duplicate keys) precisely because it makes matching ambiguous; this course's simplified version doesn't reproduce the warning, only the underlying data structure that makes the collision possible.

09

What's Next

You can now diff whole lists, not just single positions. But every reconciliation so far assumes work always needs to happen. Module 10 is the opposite move: proving a subtree can be skipped entirely — no diff, no fiber visit — when its props are reference-equal to last time. That's the bailout, and it's the reason "don't create new objects in render" is a real performance rule, not folklore.
