Module 05Double Buffering

Module 03 reserved a field called alternate and never used it. This module is where it finally does something — and where "an update never shows you a half-finished tree" stops being a promise and becomes a mechanical consequence of there only ever being two objects.

The whole claim, once — everything else is consequence

At any tree position, there are at most two fiber objects, forever — current (on screen now) and workInProgress (being built). A new render reuses current.alternate if it exists instead of allocating a third. "Committing" is flipping one pointer to say which of the two is real.

05

The Big Analogy

A photo studio has exactly two prints of the current portrait on the wall stand — never one, never three. When a new sitting happens, the retoucher doesn't buy a fresh sheet of photo paper; they pull the other print off a shelf behind the stand (the one that was on display two sittings ago) and work on that one. When it's ready, they swap which print is on the stand and which is on the shelf. The one now on the shelf is not thrown away — it's exactly what gets pulled out and reused next time.

A visitor looking at the wall never sees a half-retouched print. They either see the old one, or — after one single swap — the new one. There is no moment where the stand holds something half-finished, because the retoucher never touches the print that's currently on display.

05

What Happens, Step by Step

Four renders of the same component in a row:

  1. Render 1 (mount): Fiber A is created. A.alternate is null — there's no second buffer yet, because there's been no update yet.
  2. Render 2: createWorkInProgress(A, newProps) is called. A.alternate is null, so a genuinely new fiber B is created. B.alternate = A and A.alternate = B — set once, in both directions.
  3. Commit: the container's .current pointer flips from A to B. One assignment. B is now "current."
  4. Render 3: createWorkInProgress(B, newerProps) is called. B.alternate is A — not null — so A is reused, just given new pendingProps. No third object is ever created.
  5. Commit: .current flips back to A.
  6. Render 4: createWorkInProgress(A, ...) finds A.alternate === B, reuses B. The cycle repeats, forever, between exactly these two objects.

A Map of the State

After render 2 — two objects, linked

After the commit (one pointer flip)

  1. Bnow current — alternate→A
  2. Anow the free buffer — alternate→B

The Code, Explained

Pool-or-create, verified against real React's actual function

export function createWorkInProgress(current, pendingProps) {
  let workInProgress = current.alternate;

  if (workInProgress === null) {
    workInProgress = createFiber(current.tag, current.key, pendingProps);
    workInProgress.alternate = current;
    current.alternate = workInProgress;      // ← linked ONCE, ever
  } else {
    workInProgress.pendingProps = pendingProps;
    workInProgress.flags = 0;
  }
  // ...copy tree-shape fields from current, either way...
  return workInProgress;
}

Verified structurally against real react-dom.development.js:28183-28256: same branch, same "link both ways exactly once" behavior, same reuse-and-overwrite behavior on the pool-hit path.

The swap is one line

container.current = wip2;   // that's the whole commit, from this module's view

Nothing about this line is partial. Before it runs, every reader of container.current sees the fully-built old tree. After it runs, every reader sees the fully-built new tree. There is no third state.

Crazy detail — this course's own test caught itself making the exact mistake this module is about

The first draft of verify.mjs failed. Not because doubleBuffer.js was wrong — because the assertion re-read current1.alternate === null at the very end of the script, by which point current1.alternate had long since been reassigned to wip2. current1 is a live, mutable object; asking it a question after the story has moved on gets you the current answer, not the answer from when you first cared. The fix: capture each boolean into a const the moment it's actually true, and assert on the frozen value. It's hard to find a cleaner, more literal illustration of why real React never mutates the current object mid-render — only workInProgress — than watching this course's own verification script fall into that exact hole and climb back out.

Brain Exercise

Before reading on: if a render is started (a workInProgress tree begins being built) but is abandoned before committing — say, a newer, higher-priority update interrupts it — what has to be true about current at that moment for the abandonment to be "free" (no cleanup required)?

Work it out, then check

current must be completely untouched — every field on every current fiber has to still describe exactly what's on screen, because nothing about the abandoned render was ever allowed to write into it. All of the half-finished work lives entirely on the workInProgress side, which nobody but the renderer itself was ever looking at. Abandoning it is as simple as never calling the one line that swaps container.current — the "on-screen" tree was never at risk, because it was never the tree being mutated. This is the real reason interruptible rendering (Module 07, Track 2's A3) is safe to build at all: the thing that would need "undoing" if you stopped halfway was never visible to begin with.

05

There Are No Dumb Questions

Why not just deep-clone the tree each render instead of this pooling scheme?

Two reasons visible from this module alone: allocation cost (cloning N nodes every render vs. reusing N already-allocated nodes forever), and — more importantly for this course — it would break the "current is never mutated" guarantee only if the clone were shallow; a deep clone actually gets you the same safety property, just at a higher constant cost per render. Real React chose pooling specifically to keep that cost bounded at exactly 2× the tree size, permanently, rather than paying an allocation proportional to tree size on every single render.

Is `alternate` symmetric — does `A.alternate.alternate` always equal `A`?

Yes, and `verify.mjs` shows it implicitly: `wip2.alternate === current1` and `current1.alternate === wip2` are both asserted true right after the link is made, and neither link is ever changed afterward (only pendingProps and tree-shape fields on the fibers are). Once two fibers are paired, they stay paired for the rest of the program.

Does the container's `.current` swap need to happen "atomically" in some special JS sense — a lock, a transaction?

No — JavaScript's single-threaded execution model already guarantees a single property assignment can't be observed half-done by any other code, because no other code can run in the middle of one synchronous statement. "Atomic" here just means "one assignment, not several," which is sufficient given that guarantee. This is a case where a mechanism that would need real synchronization primitives in a multi-threaded language is free in JS.

What happens to the OLD current tree's fibers after a swap — are they garbage collected?

Not immediately, and not in this course's simplified model either: the old current becomes the new workInProgress-in-waiting, reachable via the new current's `.alternate`. It stays alive, on purpose, specifically so it's available to be reused on the very next render — which is exactly what `wip3 === current1` demonstrates.
