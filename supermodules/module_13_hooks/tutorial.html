Module 13Hooks as a Linked List on the Fiber

Every component so far has been a pure function of its props — call it twice with the same input, get the same output, no memory. This module gives a fiber its own memory, and proves, on a real schedule, exactly why that memory's addressing scheme makes "don't call hooks conditionally" a mechanical fact, not a style rule.

The whole claim, once — everything else is consequence

Hooks are a linked list stored on fiber.memoizedState, addressed purely by how many times a hook function has already been called this render — never by name, never by which line of source code called it.

The Big Analogy

Recall P5's coat-check that assigns hooks by arrival order, not by name. This module builds the real coat-check ledger: a chain of tickets, ticket #1 stapled to ticket #2, stapled to ticket #3, and so on — one chain per customer (fiber), re-read from the start on every visit. The attendant never looks at your face. They only ever ask "is this your first, second, or third item today?" and walk that many staples down the chain.

If you hand over only two items on a visit where you usually hand over three, the chain that gets rebuilt this time is one staple shorter — nothing goes wrong yet. It goes wrong the NEXT time you show up with three items again, and the attendant, expecting a chain that's only two staples long from last time, runs out of chain to walk.

What Happens, Step by Step

A component calling useState(0) then useState('clicks'), across a mount and an update:

  1. Mount (fiber.alternate === null): each useState call runs mountWorkInProgressHook — allocates a fresh hook node, appends it to the fiber's list (first call sets fiber.memoizedState; later calls extend via .next).
  2. Calling setCount(5) later doesn't change anything immediately — it pushes 5 onto that hook's queue.pending array.
  3. Update (fiber.alternate !== null, via Module 05's createWorkInProgress): each useState call now runs updateWorkInProgressHook — advances a cursor through the OLD fiber's hook list, cloning each node forward into a brand-new list on the new fiber.
  4. While cloning the "count" hook, its pending queue ([5, c => c+1]) is applied in order: 0 → 5 → 6. The "clicks" hook has an empty queue, so it just carries its value forward unchanged.
  5. The OLD fiber's hook list is never touched — same guarantee as Module 05, one level deeper.

The Code, Explained

Addressed by position, not name — verified against real React

function updateWorkInProgressHook() {
  const nextCurrentHook = currentHook === null
    ? currentlyRenderingFiber.alternate.memoizedState   // first hook this render
    : currentHook.next;                                 // Nth hook: walk N-1 times

  if (nextCurrentHook === null) {
    throw new Error('Rendered more hooks than during the previous render.');
  }
  currentHook = nextCurrentHook;
  // ...clone currentHook into a new node on the new fiber's list...
}

Verified against real React's actual function of the same name (line-cited in DECISIONS.md). Nothing here ever reads a variable name, a line number, or which specific hook function was called — only "how many times have we advanced this render."

useState is useReducer in a costume

function basicStateReducer(state, action) {
  return typeof action === 'function' ? action(state) : action;
}
// real React: function updateState(initialState) { return updateReducer(basicStateReducer); }

This is why setCount(5) and setCount(c => c + 1) both work — action is checked for being a function at dispatch time, not at the call site.

Limits — What You Cannot Do Yet

Can't do yet
  • Trigger an actual re-render when setState is called — this module's setState only queues; nothing here schedules Module 06's work loop to run again (that wiring is Module 14's job).
  • Skip a re-render based on priority — the pending queue is a plain array, applied in full, in order, every time. No lanes, no skipping (Track 2's territory).
  • useEffect, useMemo, useRef — this module builds exactly enough hook infrastructure for useState; the same linked-list mechanism generalizes to those, but they aren't built here.

If you've ever seen this error appear on a render that "looks fine" by itself, this is why — the actual mistake was one render earlier.

Brain Exercise

Before reading on: two components, A and B, each call useState exactly twice, in the same order, every render. Do they ever risk reading each other's hook state by accident?

Work it out, then check

No — and the reason is worth being precise about: each fiber has its OWN memoizedState field, its own independent hook linked list. "Addressed by call order" means "by position within one fiber's own list," never globally. currentlyRenderingFiber is reset by prepareToUseHooks before every component's render specifically so mountWorkInProgressHook/updateWorkInProgressHook always write into the CURRENT fiber's list, never some other fiber's. Two components can call hooks in the exact same order with zero risk of cross-talk, because "order" is scoped per-fiber from the start.

There Are No Dumb Questions

Why does the update path CLONE the old hook instead of just reusing the same object?

Same reason Module 05 double-buffers fibers instead of mutating one tree in place: the OLD fiber (and everything reachable from it, including its hooks) needs to stay exactly as it was, in case this render gets abandoned (Module 07) or something needs to compare "before" against "after." Mutating the old hook directly would mean there's no "before" left to compare against.

What actually happens, in this module's code, if you call a hook OUTSIDE of a render (no `prepareToUseHooks` call first)?

currentlyRenderingFiber would be null, and the very first line of mountWorkInProgressHook/updateWorkInProgressHook that touches currentlyRenderingFiber.memoizedState would throw a TypeError reading a property of null. Real React's actual error message for this exact situation ("Invalid hook call...") is friendlier, but the underlying mechanical cause — no fiber is currently "the one being rendered" — is the same.

Does the plain-array pending queue actually behave differently from real React's circular linked list, in any case this course would notice?

Not for anything Track 1 exercises — both process pending updates in the order they were queued, via the same reducer, arriving at the same final state. The behavioral difference only shows up under CONCURRENT rendering with mixed priorities, where real React's queue can skip a lower-priority update temporarily and resume it later — a scenario this course's engine has no mechanism to even construct (no lanes), which is exactly why the simplification is safe here and explicitly flagged as narrower scope in DECISIONS.md.

Is `fiber.memoizedState` overloaded to mean two different things depending on fiber type?

Yes, and that's a real, verified fact about React's actual fiber shape, not an artifact of this course's simplification — the same field name is genuinely repurposed: for a `HostComponent`/`HostText` fiber it's unused by this course's engine; for a `FunctionComponent` fiber, it's the head of the hook linked list. Real React does the same field-reuse across different fiber tags for several fields, not just this one — a space-saving convention from treating `Fiber` as one shared object shape rather than a different class per tag.
