Module 11The Effect List

If you've read about React's internals anywhere, you've probably read about "the effect list" — a linked list of every fiber with work to do, built during rendering. Grep the actual, installed React source in this repo for it, and you'll find nothing. This module builds what's really there instead.

The whole claim, once — everything else is consequence

There is no separate list. Every fiber bubbles a subtreeFlags bitmask up to its parent as rendering completes — "does anything inside me need committing?" — and commit re-walks the same tree, skipping any branch whose bit says no.

11

The Big Analogy

An apartment building's fire inspector doesn't carry a separate clipboard listing every unit with a problem, compiled floor by floor as they go. Instead, each floor's supervisor reports one bit of information up to the building manager: "is there ANYTHING on my floor that needs attention — yes or no." The building manager, holding just those yes/no bits per floor, does a second walkthrough — and skips every floor whose supervisor said no, entirely, never opening a single door on that floor.

The information that mattered was never "here's the list" — it was "here's whether it's worth looking here at all," reported once per floor, bubbled up from whoever actually checked each unit.

What Happens, Step by Step

Given a tree where exactly one deeply-nested fiber (leafC1a) has flags |= Placement, everything else untouched:

  1. As each fiber COMPLETES (bottom-up — Module 06's completeUnitOfWork position), bubbleProperties runs: OR every immediate child's subtreeFlags | flags into this fiber's own subtreeFlags.
  2. leafC1a itself has no children, so its subtreeFlags stays NoFlags — but its OWN flags has Placement set directly.
  3. leafC1 (its parent) bubbles: sees leafC1a.subtreeFlags | leafC1a.flags includes Placement → leafC1.subtreeFlags now has it too.
  4. branchC bubbles the same way from leafC1 → also picks up the bit.
  5. branchA and branchB, whose entire subtrees never changed, bubble up NoFlags — nothing to report.
  6. root bubbles from all three branches → ends up with Placement set, because AT LEAST ONE child (branchC) had it.
  7. A second walk, collectEffects, starts at root. At every fiber, it checks: is subtreeFlags === NoFlags? If so — stop, don't descend. branchA and branchB's entire subtrees are skipped this way, never visited.

The Code, Explained

bubbleProperties — one level, bottom-up, verified against real React

export function bubbleProperties(completedWork) {
  const didBailout = completedWork.alternate !== null
    && completedWork.alternate.child === completedWork.child;   // ← Module 10's exact signature

  if (didBailout) {
    completedWork.subtreeFlags = completedWork.alternate.subtreeFlags;  // copy, don't recompute
    return;
  }

  let subtreeFlags = NoFlags;
  let child = completedWork.child;
  while (child !== null) {
    subtreeFlags |= child.subtreeFlags;
    subtreeFlags |= child.flags;
    child = child.sibling;
  }
  completedWork.subtreeFlags |= subtreeFlags;
}

Verified byte-for-byte against real bubbleProperties (line-cited in DECISIONS.md) — including the bailout short-circuit, which directly reuses Module 10's exact "did this fiber bail out" evidence.

collectEffects — the pruned second walk

function walk(fiber) {
  visitCount.value++;
  if (fiber.flags !== NoFlags) effects.push(fiber);
  if (fiber.subtreeFlags === NoFlags) return;   // ← the entire branch stops here
  let child = fiber.child;
  while (child !== null) { walk(child); child = child.sibling; }
}

Verified against real React's actual commit-phase walk condition (line-cited in DECISIONS.md): descend only if subtreeFlags says there's something inside worth finding.

Brain Exercise

Before reading on: if a SINGLE leaf fiber at the very bottom of a very deep, otherwise-unchanged tree gets a Placement flag, how many fibers end up with a non-NoFlags subtreeFlags after bubbling — one, or more than one?

Work it out, then check

Every fiber on the direct path from that leaf up to the root — not just one. Bubbling is cumulative going up: the leaf's parent picks up the bit from the leaf, the grandparent picks it up from the parent, and so on, all the way to the root. A single change at depth 10 means 10 fibers (the leaf plus its 9 ancestors) all end up with a non-zero subtreeFlags, even though only the leaf itself has a non-zero flags. This is exactly why collectEffects's pruning check has to be subtreeFlags === NoFlags, not flags === NoFlags — the ancestors of a real change must NOT be pruned, even though they didn't change themselves, because something inside them did.

There Are No Dumb Questions

So did "the effect list" ever really exist, or is that just internet folklore?

It really existed — React 16 and 17's actual reconciler maintained a genuine `firstEffect`/`nextEffect`(-as-a-field)/`lastEffect` linked list, built incrementally during the complete phase. It was removed in favor of the `subtreeFlags`-bubbling approach this module builds, as part of React 18's broader internal rework. Older blog posts, conference talks, and even some still-circulating diagrams describe the old mechanism accurately for the React version they were written about — they're not wrong, they're describing a different (earlier) React.

Why bother bubbling flags at all — why not just walk the whole tree every commit and check each fiber's own `flags`?

Because that walk would visit every fiber regardless, defeating the entire performance point. `verify.mjs`'s numbers make the payoff concrete: with bubbling, 2 of 8 fibers are skipped entirely; in a real app with thousands of DOM nodes and a small, localized update, the fraction skipped is far larger. The bubbled bit is cheap to compute (one pass, already required by the render phase) and expensive to skip checking (a commit-phase walk over a huge, mostly-unchanged tree).

Does a bailed-out fiber ever need re-bubbling later, if nothing about it changes?

Not until something downstream of it actually changes again — at which point THAT fiber's own bailout check would fail (its child pointer would differ from its alternate's), and bubbling would run for real, all the way back up through every ancestor on the path, including this one. The copy-forward behavior is only valid for exactly as long as the "nothing changed" evidence holds.

Is `subtreeFlags` the same bit values as `flags`, just on a different field?

Same universe of bit values (`Placement = 2`, `Update = 4`, etc. — real, shared constants), different meaning: a fiber's own `flags` means "something about THIS fiber needs committing"; its `subtreeFlags` means "something SOMEWHERE inside my children needs committing." A fiber can have `flags = NoFlags` (nothing wrong with it directly) and `subtreeFlags = Placement` (something below it needs placing) at the same time — exactly `leafC1`'s and `branchC`'s situation in this module's example.
