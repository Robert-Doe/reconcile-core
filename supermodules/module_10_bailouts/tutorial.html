Module 10Bailouts & Memoization

Every module so far assumed a fiber's work needs doing. This module proves the opposite can happen: an entire subtree — not just one fiber, everything below it — can be skipped completely, and the proof isn't "render wasn't called," it's that nothing downstream was even touched.

The whole claim, once — everything else is consequence

The bailout check is reference equality, not shallow equality: current.memoizedProps === pendingProps. An object with identical values but a different reference does not qualify on its own — memo exists specifically to make it qualify, by substituting the old reference.

The Big Analogy

An inspector re-certifying a building doesn't re-inspect every room every year. They check one thing first: is this the exact same folder of blueprints that was already certified — not a photocopy with identical contents, the literal same folder, same paperclip, same coffee stain? If yes, certification is instant: nothing downstream (the rooms, the wiring, the plumbing) gets a second look. If it's a new folder — even one that, word for word, says the same thing as the old one — full inspection, every room, from scratch.

A building owner who wants the fast path back has one option: hand the inspector the same folder next time, not a fresh copy. That's what memo does — it's not a smarter inspector, it's a filing clerk who checks a new folder against the old one first and, if they match word for word, quietly staples the OLD folder to the inspector's clipboard instead.

What Happens, Step by Step

beginWorkWithBailout(current, workInProgress, renderComponent):

  1. Is this an update (current !== null)? Mounting never bails — there's nothing to compare against.
  2. Is current.memoizedProps the exact same object as this render's pendingProps? Checked with ===, not a value comparison.
  3. Was there a scheduled update on this fiber anyway (e.g. a state change)? If so, no bailout — something local demands a re-render regardless of props.
  4. All conditions met → bail: workInProgress.child = current.child — the exact same child fiber(s), not a clone, not a fresh visit. renderComponent is never called.
  5. Any condition fails → do the real work: call renderComponent, let normal reconciliation (Modules 04/08/09) produce the new children.

The Code, Explained

The bailout check — verified against real React's exact structure

export function shouldBailout(current, pendingProps, hasScheduledUpdate) {
  if (current === null) return false;
  const oldProps = current.memoizedProps;
  if (oldProps !== pendingProps) return false;   // ← reference check, not value check
  if (hasScheduledUpdate) return false;
  return true;
}

Verified against real React's actual condition (line-cited in DECISIONS.md): if (oldProps !== newProps || hasContextChanged() || ...) { didReceiveUpdate = true; } — same polarity, same reference operator.

memo's real trick, quoted from React's own source comment

export function resolveMemoProps(current, nextProps, arePropsEqual = shallowEqual) {
  if (current === null) return nextProps;
  const prevProps = current.memoizedProps;
  if (arePropsEqual(prevProps, nextProps)) {
    return prevProps;   // ← "Reuse the previous props object,
  }                       //    like we would during a normal fiber bailout."
  return nextProps;
}

That comment is copied, verbatim, from real react-dom.development.js at the exact line this substitution happens. memo is not a rival bailout mechanism — it feeds the same one.

The proof that nothing downstream was touched

if (shouldBailout(current, workInProgress.pendingProps, hasScheduledUpdate)) {
  workInProgress.child = current.child;   // SAME reference — no clone, no visit
  workInProgress.memoizedProps = workInProgress.pendingProps;
  return workInProgress.child;
}

Limits — What You Cannot Do Yet

Can't do yet
  • Track "a scheduled update" with any real priority system — modeled here as a plain boolean, not real React's lane bitmask (Track 2's A3 territory).
  • Bail out based on context changes — this course hasn't built a context mechanism at all.
  • Explain hooks-based memoization (useMemo/useCallback) — those memoize *values passed as props*, one level up from this module's concern, which is what happens once a fiber *receives* a possibly-new props object.
Can do
  • Explain precisely why "props look the same" and "React will skip this" are different claims, with a real counterexample.
  • Explain what memo mechanically does — and that it isn't magic, it's reference substitution feeding an existing check.
  • Prove, not assert, that a bailout touches zero fibers below the one it fires on.

Brain Exercise

Before reading on: a parent component does <Child data={{ id: 1 }} /> directly in its JSX, every render. Would wrapping Child in memo help it bail out, ever?

Work it out, then check

No — and this is the single most common way people misuse memo and then conclude it "doesn't work." {{ id: 1 }} is a fresh object literal, created new on every single call to the parent's render function, no matter how many times its values happen to match. memo's shallowEqual check would actually catch this correctly — {id:1} shallow-equals {id:1} — so in THIS specific case memo genuinely would help (`resolveMemoProps` would substitute the old reference and the bailout would fire). The much worse, common case is when the object contains a nested object, a function, or an array as one of its OWN values — shallow equality only checks one level deep, so `{ config: { id: 1 } }` twice will shallow-compare `config`'s two different inner objects by reference and fail, even though `memo` is doing exactly what it's supposed to.

There Are No Dumb Questions

Is this why "don't create new objects/arrays/functions inline in render" is a performance rule?

Precisely this. `` builds a brand-new object every render — even wrapping `Child` in `memo` can't help, because the new object will never be reference-equal OR shallowly-equal-but-actually-different-in-a-way-that-matters to anything meaningful across renders in the way that matters for THIS specific check when it's the direct prop itself vs. nested. The rule isn't superstition; it's a direct, mechanical consequence of this module's `shouldBailout` requiring `===`.

If bailing out reuses `current.child` by reference, and that child fiber still has an `alternate` pointing back at itself, is anything about double buffering violated?

No — this is actually double buffering working exactly as designed. The reused child fiber's `alternate` still points at whatever it always pointed at; nothing about the swap-two-buffers mechanism from Module 05 cares whether a NEW workInProgress fiber was allocated for a given position this render. A bailout just means: for this position, this render, the answer to "what should workInProgress look like here" was "identical to current," so we didn't bother allocating a third state to represent that.

Does a bailout mean the component's function never runs again, ever?

No — it means it doesn't run THIS render. The very next render, if props genuinely change (a new, non-shallowly-equal object, or a scheduled state update fires), `shouldBailout` returns `false` again and the component renders normally. Bailouts are a per-render decision, re-evaluated every time, never a permanent "this component is frozen" state.

Why does a scheduled update override the bailout even if props are unchanged?

Because a fiber's own local state (Module 13's hooks) can change independently of what its parent passes in. If a component called `setState` internally, its next render needs to reflect that new state regardless of whether its props object happens to be the same reference as last time — bailing out in that case would mean the state update never visibly takes effect, which would be a real, user-visible bug, not an optimization.
