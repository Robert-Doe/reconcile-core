Module 03The Fiber Node & Linked-List Tree

Elements (Module 01-02) are data about intention, built fresh every render, thrown away immediately. A fiber is different: it's a durable node that persists across renders, and it's held together by exactly three pointers — no array-of-children field anywhere.

The whole claim, once — everything else is consequence

A fiber tree stores child, sibling, return per node — first child, next sibling, parent — and nothing else describes its shape. Every child of a node is reached by following child once, then sibling repeatedly. This is real React's actual field layout, not a simplification invented for this course.

The Big Analogy

Recall Module 01's furniture-shop work orders. A fiber is the shop's actual job ticket — the internal paperwork the shop itself keeps, one per job, stapled together not by a master list of "all jobs for this customer" but by handwritten notes in the corner of each ticket: "next job for the same customer →," and "the job that sent us this one ↑." No ticket has a list. Every ticket only knows its immediate neighbors.

You can still find every job for a customer — you just have to start at their first ticket and keep following the "next job" note until it's blank. It's slower to look up than an array would be. But it means the shop can hand you one single ticket and you have everything you need to keep walking, indefinitely, without ever holding "the whole list" in your hands at once. That property — never needing the whole structure in hand — is the entire reason Module 06's loop can pause partway through and pick a single ticket back up later.

03

What Happens, Step by Step

Building the tree App → [Header, Main → [Text], Footer] with appendChild:

  1. appendChild(App, Header) — App.child is null, so Header becomes it directly. Header.return = App, Header.index = 0.
  2. appendChild(App, Main) — App.child is already Header, so walk Header.sibling (currently null) and attach Main there instead. Main.return = App, Main.index = 1.
  3. appendChild(App, Footer) — walk to the end of the sibling chain (Header → Main) and attach after Main. Footer.index = 2.
  4. appendChild(Main, Text) — a different parent. Main.child is null, so Text becomes it directly, with its own independent return/index.

Nowhere in any of this does anything append to an array. Every "child" relationship is one object's field pointing at another object.

Brain power

forEachFiber's real, executed output (see Run It) is App → Header → Main → hi → Footer. Notice it's depth-first: Main's child Text is visited immediately after Main, before Footer — even though Footer is "closer" to Main in the sibling chain. Parent-before-children, and a whole subtree before its next sibling, always.

The Code, Explained

The fields that matter, verified against real React

// fiber.js — see DECISIONS.md for the full real-source citation
this.return = null;   // parent
this.child = null;    // first child
this.sibling = null;  // next sibling
this.index = 0;       // position among siblings

These four field names and their meaning are a direct transcription of real react-dom@18.3.1's internal FiberNode constructor (line-numbered citation in DECISIONS.md). We didn't invent "return" as a parent-pointer name — it's real React's actual name, chosen (per the surrounding source) because a fiber's return pointer is where execution returns to once this fiber's subtree is done, echoing a function call's return address.

Traversal: down, across, up — one loop, three rules

export function forEachFiber(root, visit) {
  let next = root;
  while (next !== null) {
    visit(next);
    if (next.child !== null) { next = next.child; continue; }
    let node = next;
    while (node !== null && node.sibling === null) node = node.return;
    next = node === null ? null : node.sibling;
  }
}

Three rules, checked in order, every iteration: go down if there's a child; otherwise go up until you find an ancestor with an unvisited sibling, then go across to it. This is exactly P3's explicit-loop pattern, now over the real fiber shape instead of a toy tree.

Limits — What You Cannot Do Yet

Can't do yet
  • Build a fiber tree from an element tree automatically — this module's tree was wired by hand, with explicit appendChild calls. That's Module 04.
  • Update anything — there's only one tree; nothing here represents "last render" vs. "this render" (that's alternate, deliberately left null, reserved for Module 05).
  • Pause the traversal — forEachFiber runs straight through to completion. Module 06/07 make the loop interruptible.
Can do
  • Represent any tree shape using only child/sibling/return/index.
  • Correctly enumerate an entire tree, depth-first, parent-before-children, using an explicit loop instead of recursion.
  • Point to the exact real-React source lines every field name and its purpose came from.

Brain Exercise

Before reading on: suppose Main had two children, Text1 and Text2, instead of one. Which single field, on which single fiber, has to change for forEachFiber to discover both without any change to forEachFiber itself?

Work it out, then check

Only Text1.sibling needs to become Text2 (and Main.child still points at Text1, unchanged). forEachFiber never asked "how many children does this node have" — it only ever asks "does this node have a child" and "does this node have a sibling," both yes/no questions answerable from a single node in isolation. That's the payoff of P2's design: the traversal function's code doesn't scale with fan-out at all.

03

There Are No Dumb Questions

Why not just store an array of children — wouldn't that be simpler to read?

To read, arguably yes. But Module 06's work loop needs to be able to pause mid-traversal and resume later from a single saved reference. With an array-of-children shape, "where was I" requires remembering which array, which index into it, and a stack of outer arrays/indices you were nested inside — effectively reinventing the call stack as data. With return/child/sibling, "where was I" is just one fiber reference; return already encodes the entire path back to the root.

What's the difference between a fiber and an element, concretely?

An element (Module 01) is thrown away and rebuilt from scratch every single render — it's ephemeral by design. A fiber persists across renders; the same fiber object is reused and mutated (its pendingProps updated) when possible, which is precisely what lets Module 10's bailout logic compare "new props" against "props from last time" — there has to be a "last time" object still around to compare against, and elements don't provide one.

Real React's fiber has ~25 fields. Is dropping 16 of them going to bite me later in this course?

No — every dropped field is either DEV-only profiling instrumentation (zero reconciliation behavior) or belongs to a mechanism this course handles differently by design (hooks state, in Module 13, uses its own simplified per-fiber storage rather than wiring into real React's exact memoizedState/updateQueue hook-list format). Each is named explicitly in DECISIONS.md so you know it was a decision, not an oversight.

Is index just "which position in props.children's array"?

For now, effectively yes — but hold that thought for Module 09. Once elements can be reordered between renders (a keyed list where item 3 moves to position 1), a fiber's index becomes the thing that tells the diff algorithm "did this item move?" — comparing where a fiber's key was last render against where it is this render. It stays interesting precisely because it's not just "array position," it's "last known array position," which can now disagree with the incoming data.
