Module 02JSX Desugaring by Hand

JSX is not the API. It's the one part of this entire course that never runs in a browser — it's erased before your code ships, by a compiler. This module proves that, using the actual compiler this repo's dev server runs, on real source, with the real compiled output printed in full below.

The whole claim, once — everything else is consequence

<div className="card">{children}</div> is erased at build time into jsx("div", { className: "card", children }) — a plain function call. And it is not React.createElement by default anymore: modern tooling emits calls to jsx/jsxs from react/jsx-runtime, a different calling convention Module 01 didn't cover.

P7 · What "after bundling" means
02

The Big Analogy

JSX is a court stenographer's shorthand. In the courtroom, someone says "the witness nodded and said 'yes.'" The stenographer never writes that sentence — they write compressed shorthand symbols, fast, in the moment. Nobody in the room reads shorthand at trial. Later, an entirely separate transcription pass expands every symbol back into full sentences for the official record.

JSX is the shorthand. The compiler (in this repo: esbuild, the same one Vite's dev server calls) is the transcriptionist. By the time your code runs in a browser, no JSX exists anywhere — only the expanded, boring, ordinary function calls it was shorthand for. If you've only ever read the shorthand, this module is where you sit down with the transcript.

02

What Happens, Step by Step

From source to running code, for <span>only one child</span>:

  1. Your editor/bundler feeds the .jsx source text to a compiler. In this repo: Vite hands it to esbuild.
  2. The compiler counts the JSX element's children in the source text, at compile time — before anything runs.
  3. Zero or one child → the compiler emits a call to jsx(type, props). Two or more → it emits a call to jsxs(type, props), with props.children already built as an array.
  4. The compiler also inserts import { jsx, jsxs } from "react/jsx-runtime" at the top of the file automatically — you never write this import yourself.
  5. At run time (not compile time), jsx/jsxs execute: extract key/ref, copy remaining props, backfill defaultProps, return the same { $$typeof, type, key, ref, props } shape Module 01 built.
03

A Map of the State — the Real Compiled Output

This is not a paraphrase. This is esbuild.transformSync()'s actual return value, for real JSX source, using the exact jsx: 'automatic' setting this repo's vite.config.js implies via @vitejs/plugin-react's default:

Input — real .jsx source 
export function Greeting({ name }) {
  return (
    <div className="card">
      <h1>Hello, {name}</h1>
      <p>welcome</p>
    </div>
  );
}
Output — esbuild's real, unmodified compiled code 
import { jsx, jsxs } from "react/jsx-runtime";
function Greeting({ name }) {
  return /* @__PURE__ */ jsxs("div", { className: "card", children: [
    /* @__PURE__ */ jsxs("h1", { children: [
      "Hello, ",
      name
    ] }),
    /* @__PURE__ */ jsx("p", { children: "welcome" })
  ] });
}
Brain power

Notice <div> and its immediate <h1> both compile to jsxs (they have 2 and 2 children respectively — the div has an h1 and a p; the h1 has "Hello, " and {name}), while <p> compiles to jsx (exactly one child, the string "welcome"). No import statement told the compiler which to use — it counted, per element, in your source text.

04

The Code, Explained

One implementation, two exported names

// jsx.js
export function jsx(type, config, maybeKey) {
  return jsxImpl(type, config, maybeKey);
}
export function jsxs(type, config, maybeKey) {
  return jsxImpl(type, config, maybeKey);   // identical body
}

Verified against real React's own source: react-jsx-runtime.development.js literally assigns var jsx = jsxWithValidationDynamic; var jsxs = jsxWithValidationStatic; — two named bindings, functionally the same core path today. We're not cutting a corner by making them identical; real React ships them identical too.

Children are pre-assembled, not counted at runtime

Compare Module 01's createElement(type, config, ...children) — which received children as separate arguments and counted them — against this module's jsx(type, config, maybeKey), which receives exactly three arguments no matter how many JSX children there were, because config.children was already built by the compiler. This is the load-bearing difference between the classic and automatic JSX runtimes, proven directly by the "Dispatch proof" run below.

Crazy detail — this course's own verification script failed the first time

When this module was built, the first run of verify.mjs reported match: false for the nested Greeting case, while the flat SingleChild case passed. The cause: the comparison function stripped real React's dev-only _owner/_store fields only at the top level of the element, not recursively — so a top-level match still failed because the nested h1/p children (elements themselves) still carried those extra fields untouched. Fixing the comparison to recurse through props.children made it pass. This is left in the DECISIONS.md and here on purpose: verifying against real output catches real mistakes, including in the verification code itself — that's the entire point of running it instead of asserting it.

07

Brain Exercise

Before reading on: a component returns <>{a}{b}{c}</> — a Fragment with three expression children. Does this compile to jsx or jsxs? And separately — does it matter, at the level this course cares about, whether it's a Fragment or a div?

Work it out, then check

Three children, so jsxs — the compiler counts children in the source regardless of what type is; a Fragment is just type = Symbol.for('react.fragment') instead of a string, but it flows through the identical jsx/jsxs call machinery. The dispatch rule is entirely about child count, never about which tag/type is being created. This is also why jsxImpl in jsx.js never inspects type except to look up defaultProps — everything else it does is type-agnostic.

08

There Are No Dumb Questions

I've read that JSX compiles to React.createElement. Was that ever true, and is it still?

It was and, with the "classic" runtime setting, still is — some tools still default to it or can be configured to. But every current default (Create React App's newer templates, Vite + @vitejs/plugin-react, Next.js) uses the "automatic" runtime this module builds, which emits jsx/jsxs from react/jsx-runtime instead, and does not require you to have React in scope at all (no more import React from 'react' just to use JSX). Module 01's createElement isn't wrong — it's the older convention, still shipped, no longer what a fresh JSX file compiles to by default.

Why does the compiler bother with two functions (jsx/jsxs) if they do the same thing right now?

Per real React's own source comment (quoted in DECISIONS.md), it's forward-looking: shipping the distinction now means a future React version can specialize jsxs's implementation to skip work that's only safe when children are a known-static list, without a breaking change to the call sites. You're seeing an API designed for an optimization that hasn't landed yet.

Does this mean JSX and createElement produce genuinely incompatible elements?

No — verify.mjs's field comparison shows the exact same element shape ($$typeof, type, key, ref, props) comes out either way. What differs is only the calling convention getting there (varargs + runtime counting vs. pre-built props + compile-time dispatch), never the resulting data.

If I never write JSX and always call jsx()/createElement() myself, am I missing anything?

Not for anything this course covers. JSX is purely an authoring convenience erased before runtime — every module from here on operates on the element/fiber data, which is identical either way. Real component libraries occasionally hand-call jsx() directly (skipping JSX) for exactly this reason: there's no capability gap, only an ergonomics one.
