React Reconciliation from Scratch · Track 1 · Phase 1: Elements

Module 01createElement & the Element Shape

Before there is a "virtual DOM," before there is any tree to reconcile, there is one function that returns one plain object. This module builds it — and proves, by running our version against real React 18.3.1 side by side, that a React element is nothing more than that.

The whole claim, once — everything else is consequence

createElement(type, props, ...children) returns a plain, inert JS object — { $$typeof, type, key, ref, props } — with no connection to the DOM, no rendering behavior, and no lifecycle. It is data. Nothing runs because you called it.

01

The Big Analogy

A React element is a work order, not a finished piece of furniture. Picture a form a customer fills out at a furniture shop's counter: "type: chair," "props: { color: red, legs: 4 }," "children: [a cushion work-order]." The clerk who takes this form does not build anything. They don't even check if red chairs with four legs are physically buildable. The form is just ink on paper — data describing an intention.

The actual carpenter (Module 12's commit phase) is a different person entirely, working from a different pile of paperwork (the fiber tree, Module 03+), possibly hours later. Right now, in this module, we are only building the form — and proving that filling it out twice with the same handwriting produces two different pieces of paper, even if every word on them matches.

02

What Happens, Step by Step

Calling createElement('div', { className: 'x' }, 'hello'):

  1. An empty props object is created.
  2. If a second argument (config) was passed and isn't null: pull ref and key out of it into their own variables (never into props), then copy every other own-property of config into props.
  3. Count the remaining arguments (the children). Zero → props.children stays undefined. Exactly one → props.children is that one value, unwrapped. Two or more → props.children is an array of all of them.
  4. If type has a defaultProps object, backfill any prop that is exactly undefined (not just missing) from it.
  5. Return a new plain object: { $$typeof: Symbol.for('react.element'), type, key, ref, props }.

That's the entire function. No DOM API is touched. No global state is read or written.

03

A Map of the State

Calling createElement('p', null, 'text before ', createElement('b', null, 'bold'), ' text after') produces one object with another object nested inside its props.children array — not a tree walker's tree yet, just JS's own object nesting:

Outer element

{
  $$typeof: Symbol(react.element)
  type: "p"
  key: null
  ref: null
  props: {
    children: [
      "text before ",
      { type: "b", props: {…} }  ← same object
      " text after"
    ]
  }
}

The nested element, by itself

{
  $$typeof: Symbol(react.element)
  type: "b"
  key: null
  ref: null
  props: {
    children: "bold"
  }
}
Brain power

outer.props.children[1] === inner is true — the exact same reference (see P1), not a copy. Nothing about "nesting" here is special machinery. It's the same thing that happens when you put one plain object inside another object's array field, because that's literally what it is.

04

The Code, Explained

The tag that can't be forged

// createElement.js
export const REACT_ELEMENT_TYPE = Symbol.for('react.element');

Verified identical to real React's source at react.development.js:32. Using Symbol.for (the global symbol registry) rather than plain Symbol() is deliberate: it's the one value on Earth that JSON.parse can never produce, which is exactly why it's safe to trust el.$$typeof === REACT_ELEMENT_TYPE as proof "this came from a real createElement call," even if the object arrived from, say, a server response an attacker partially controls.

Children collapse — the part everyone gets wrong from memory

const childrenLength = children.length;
if (childrenLength === 1) {
  props.children = children[0];       // bare value, not [value]
} else if (childrenLength > 1) {
  props.children = children;          // real array
}

This asymmetry is verified against real React by verify.mjs's "span... one text child" and "ul, three li children" cases, matching byte-for-byte. It is why props.children in a real component can be a bare string or an array depending on how many children were written — any code (including yours, later, in Module 09) that assumes it's "always an array" will break on the single-child case.

Key coercion

if (hasValidKey(config)) key = '' + config.key;

A number key and a string key that print the same become the same key. This isn't cosmetic — Module 09's array diff compares keys for equality, and 1 === "1" is false in JS. Coercing here means "same key" can never silently fail later because of a type mismatch nobody intended.

05

Limits — What You Cannot Do Yet

Can't do yet
  • Render anything to a screen — there is no DOM node anywhere in this module.
  • Update anything — there's no concept of "last time" to compare against.
  • Walk a tree — nested elements sit inside props.children, but nothing here traverses that structure. That's Module 03.
  • Handle function components — type can be a function, but nobody calls it. It's stored, not invoked.
Can do
  • Build arbitrarily deep nested element structures with plain function calls.
  • Distinguish a real element from a look-alike object via isElement.
  • Reason correctly about props.children's shape (bare value vs. array) for any input.
  • Predict exactly what real React.createElement would return, for the same call — verified, not assumed.

07

Brain Exercise

Before reading on: createElement('div', { key: 1 }) and createElement('div', { key: "1" }) — do they produce elements with ===-equal key fields? And separately: are the two returned elements (the whole objects) === to each other?

Work it out, then check

Their key fields are equal: both coerce to the string "1", and "1" === "1" is true. But the two elements are two separate object literals — per P1, object equality is by reference, and createElement returns a fresh object every call. So el1 === el2 is false, even though every field you'd print from them matches. This is exactly the gap keys are built to bridge in Module 09: the diff can't use === on the element itself (always false across renders), so it uses the key field as a stand-in identity instead.

08

There Are No Dumb Questions

Is props.children always going to be a headache, given it's sometimes a string, sometimes an array, sometimes undefined?

Yes, and real React's own internal code deals with this by routing almost everything through one normalizing helper (React.Children.map/forEach, or internally mapChildren) before treating children as a list. This course does the same starting in Module 04 — we normalize once, at the boundary, rather than have every later module re-handle three possible shapes.

Why does type get to be either a string ("div") or a function (a component)? Isn't that two different things pretending to be one field?

It genuinely is two different things, and Module 04 is where the fork happens: a string type means "this becomes a real DOM node eventually," and a function type means "call this function to find out what element(s) it produces instead." createElement itself doesn't need to know the difference — it just stores whatever you gave it. The interpretation is entirely the mount phase's job.

If elements are just plain objects, could I build one by hand with { type: 'div', props: {} } and skip createElement entirely?

You could build an object with those fields, but it would fail isElement(), because it's missing the unforgeable $$typeof Symbol — which you cannot type as a JS literal from outside this module, since you'd need a reference to the exact same Symbol.for('react.element') value. That's the entire point: the shape is copyable, the tag is not.

Where did _owner and _store go? Real React's output had them.

Cut on purpose (see DECISIONS.md) — they're dev-mode-only bookkeeping (which component created this element; whether it's been validated) with zero effect on reconciliation. Every later module in this course would ignore them anyway.

This seems like too little to call a "virtual DOM." Where's the actual DOM-like structure?

There isn't one yet, and that's the point of stopping here. An element doesn't know it will ever touch a screen. The "virtual DOM" as a walkable, stateful tree doesn't exist until Module 03's fiber shape and Module 04's mount pass turn this inert data into something with parent/child/sibling relationships and a lifecycle. This module is deliberately smaller than "virtual DOM" — it's the atom, not the tree.

09

What's Next

You now have a function that produces the exact same inert data shape real React does. Module 02 takes one step backward in the pipeline you'll actually use day to day: JSX. You'll run real JSX through Babel and prove, by diffing real compiler output against hand-written createElement calls, that JSX is nothing but syntax sugar for exactly this function — no new capability, no hidden magic, one more compiler pass standing between what you write and what you just built.
