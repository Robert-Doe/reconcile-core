Trees Made ofPointers, Not Arrays

The obvious way to store a tree in JS is { children: [...] }. Fiber does not do that. It stores exactly three pointers per node — child, sibling, return — and that single decision is what makes Module 06's loop possible.

Picture a family tree drawn the way genealogists actually draw them: no node lists "my children" as a numbered array. Instead, each person has a line to their eldest child, and each sibling has a line to the next sibling over. To find "all of someone's children," you don't read a list — you walk: go to the eldest child, then keep walking sideways through siblings until the line runs out.

It's more steps per lookup. But every node now has a fixed, tiny, predictable shape — exactly three pointers — no matter how many children it has. A node with one child and a node with nine children are structurally identical to inspect.

A fiber-shaped node:

{
  child:   // first child, or null
  sibling: // next sibling (same parent), or null
  return:  // parent, or null
}

To visit every child of a node, you don't index an array — you follow child, then keep following sibling until you hit null:

function forEachChild(node, fn) {
  let n = node.child;
  while (n !== null) {
    fn(n);
    n = n.sibling;
  }
}

Why this course cares

Module 03 builds this shape. Module 06's work loop needs it specifically because a loop that walks "down, then across, then up" needs somewhere to store "where do I go next" that isn't the call stack — and return is exactly that: an explicit, inspectable "parent" pointer standing in for what a recursive call's stack frame would normally remember implicitly.
