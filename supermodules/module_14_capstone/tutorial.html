What Happens, Step by Step

Mounting <App/> (a memoized Header + a stateful Counter), then clicking increment twice:

  1. mountApp creates a fiber for App, flags it Placement, wraps it in a HostRoot, and runs the full loop: beginWork (dispatches per fiber tag, composing Modules 04/08/09/10/13) → completeUnitOfWork (Module 06's shape, fused with Module 12's DOM building) → repeat until done.
  2. commit (Module 11's pruned walk + Module 12's placement/deletion) attaches the whole thing in one real DOM operation.
  3. A click calls setCount(c => c + 1) — Module 13's useState, wrapped by this module to also call scheduleUpdate.
  4. scheduleUpdate creates a workInProgress for the top App fiber via Module 05's createWorkInProgress, with the SAME props reference — and forces it to actually re-execute (see "Limits" below).
  5. The loop runs again. Header's fiber, reached via normal reconciliation, checks Module 10's real bailout condition — passes (thanks to memo) — and is skipped entirely, not even visited below itself.
  6. Counter's fiber does NOT bail (its own hook state changed) — re-renders, and Module 09 reconciles its single changed text node in place.
  7. Commit runs again — only the changed text node gets touched.

The Code, Explained

The dispatcher — composing, not reimplementing

function beginWork(current, workInProgress, forceUpdate) {
  if (workInProgress.tag === FunctionComponent) {
    let pendingProps = workInProgress.pendingProps;
    if (current !== null && workInProgress.type.isMemo) {
      pendingProps = resolveMemoProps(current, pendingProps);   // Module 10
    }
    if (!forceUpdate && current !== null && shouldBailout(current, pendingProps, false)) {
      workInProgress.child = current.child;
      return null;                                              // ← see Bug 2 below
    }
    prepareToUseHooks(workInProgress);                          // Module 13
    const rendered = workInProgress.type(pendingProps);
    finishHooks();
    workInProgress.child = reconcileSingleChild(workInProgress,  // Module 08
      current ? current.child : null, rendered);
    return workInProgress.child;
  }
  if (workInProgress.tag === HostComponent) {
    const children = normalizeChildren(workInProgress.pendingProps.children);  // Module 04
    workInProgress.child = reconcileChildrenArray(workInProgress,              // Module 09
      current ? current.child : null, children);
    return workInProgress.child;
  }
  return null;
}

Every function called here — resolveMemoProps, shouldBailout, prepareToUseHooks, reconcileSingleChild, normalizeChildren, reconcileChildrenArray — is imported unmodified from the module that built and proved it.

Limits — What This Course Does Not Build

Explicitly out of scope
  • Event delegation — the demo app wires its own onclick directly, a documented gap since Module 12.
  • childLanes propagation — this engine forces the update's entry fiber to always re-execute rather than tracking which descendants genuinely have pending work. Real, flagged simplification (DECISIONS.md).
  • Concurrent rendering, Suspense, transitions, the real Scheduler package — Track 2's A3/A6 territory, not built here.
What the whole engine, together, can do
  • Mount a real, multi-component app and correctly render it to a real (or real-shaped) DOM.
  • Handle real state updates from a real event, through the actual hook/scheduling/diffing/commit pipeline.
  • Correctly and repeatedly bail out a memoized component while updating an unrelated stateful sibling — proven across multiple updates, not just once.

Crazy detail — two real bugs, in order, both fixed live

Bug 1: the first draft passed one stable {} reference into createElement(Header, ...) every render, expecting reference-equal props. It didn't work — createElement (correctly, per Module 01) always builds a fresh props object regardless of what config reference you pass. The fix was wrapping Header in memo, which routes props through Module 10's real shallow-equal-then-substitute trick. Bug 2: once bailout started firing, the committed HTML showed duplicated content — "Static HeaderStatic Header". The bailout branch was returning workInProgress.child to the work loop as if it were normal next-work, which made the loop revisit the OLD, uncloned h1 fiber and treat it as a fresh mount (since its own .alternate was null), creating a duplicate text node. The fix: a real bailout returns null — "nothing to descend into" — exactly matching Module 10's own thesis, which this integration had briefly failed to actually honor. Full traces of both are in DECISIONS.md.

A note on this module's own live-browser verification

As with Module 12, the in-session browser check for demo.html could not be completed — the tooling used to build this course reported itself unavailable. The Node-side proof above is real and did run, this session, against a hand-rolled DOM stand-in (Module 12's fakeDom.mjs); demo.html is written to use the genuine browser document with no shim, and should work identically when you open it.

Brain Exercise

Before reading on: if App itself were wrapped in memo too, and scheduleUpdate did NOT force the entry fiber to skip its own bailout check, what would happen when you clicked the increment button?

Work it out, then check

Nothing would happen on screen — silently. App's own props (there are none) would be reference-equal (or shallow-equal via memo) to last render's, and it has no hooks of its own with pending updates, so shouldBailout would return true for App itself. Per Module 10's real mechanism, that means App's ENTIRE child subtree — Header AND Counter — gets reused wholesale, by reference, without a single fiber inside being visited. Counter's pending state update would sit in its hook queue forever, applied to a render that never happens. This is exactly the real-world failure real React's childLanes mechanism exists to prevent — and exactly why this course's simplified engine deliberately never lets the entry fiber bail out, as a stand-in for tracking that properly.

There Are No Dumb Questions

Is this engine "real React" now?

No, and it was never trying to be — it's a small, honest, verified model of the mechanisms real React uses, with every simplification named and every real behavior checked against real source. It has no events system, no context, no Suspense, no concurrent scheduling, no error boundaries, no server rendering. What it DOES have — the fiber shape, double buffering, the work loop, keyed diffing, bailouts, the effect list, the commit split, and hooks — was checked line-by-line against real react@18.3.1/react-dom@18.3.1 throughout, which is a different and more useful claim than "this is a tiny React clone."

Why did building the integration surface bugs that building each module alone didn't?

Because each module's own tests only ever exercised the CONTRACT that module itself defines — Module 10's tests confirmed its own shouldBailout/resolveMemoProps functions behave correctly in isolation, which they do. Nothing in Module 10 alone could catch "what does the WORK LOOP do with this function's return value," because Module 10 doesn't have a work loop. Integration bugs live specifically in the gaps between correct pieces — which is exactly why this phase exists as its own module rather than being assumed to fall out for free.

If I wanted to add `useEffect` next, roughly how much of this engine would need to change?

Less than you'd think, structurally: `useEffect` is another hook, so it plugs into Module 13's existing linked-list mechanism with its own `dependencies`/`create`/`destroy` fields on the hook node. The harder part is scheduling WHEN effects run relative to commit (real React runs passive effects asynchronously, after paint) — which would mean extending this module's `commit` function to also collect and run effect callbacks, in the right order, after the DOM is attached. The fiber shape, the work loop, and the commit split wouldn't need to change at all.
