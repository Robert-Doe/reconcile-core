Module 03 · The organizing spine

The 5 Execution Mechanisms (Master Taxonomy)

Thousands of XSS payloads exist. But every one of them causes JavaScript to run through exactly one of five underlying mechanisms — or a chain of them. Learn these five and the payload zoo becomes a finite, defendable space.

Why a defender needs a taxonomy. You cannot prove a defense stops "all payloads" — the payload space is unbounded and adversarial. You can argue a defense covers a mechanism. A rigorous defensive claim has the form: "This control neutralizes mechanisms 1, 3, and 4; mechanisms 2 and 5 require these additional controls." That is the shape of your Module 18 thesis.

The five mechanisms at a glance

#MechanismEssenceCanonical proof
1 Tag parsing The parser creates a script-capable element. <script>alert(1)</script>
2 Event attributes An on* handler runs JS — no <script> needed. <img src=x onerror=alert(1)>
3 URI schemes A code-bearing URL in a navigational sink. <a href="javascript:alert(1)">
4 DOM sinks Client JS routes attacker data into an HTML/JS sink. el.innerHTML = location.hash
5 Context escape + reparse Break out of the current context, or exploit a string that mutates on re-parse (mXSS). "><svg onload=alert(1)>

Mechanism 1 — Tag parsing create a code element

The parser encounters markup that instantiates an element the browser will execute: <script>, or a <script> living inside SVG (<svg><script>), or an <iframe srcdoc> whose decoded document contains one.

<script>alert(document.domain)</script>
<svg><script>alert(1)</script></svg>
<iframe srcdoc="&lt;script&gt;alert(1)&lt;/script&gt;"></iframe>

What stops it: contextual HTML encoding (so < never starts a tag), or a CSP script-src that forbids inline script. What it targets: the tokenizer's Data → Tag-open transition (Module 02).

Mechanism 2 — Event attributes no <script> required

There are 150+ intrinsic event attributes. Any element carrying one runs JS when that event fires — and some events (onerror on a broken image, onload on <svg>, onfocus with autofocus) fire with zero user interaction.

<img src=x onerror=alert(1)>
<svg onload=alert(1)>
<input autofocus onfocus=alert(1)>
<body onpageshow=alert(1)>

This is why "block <script>" is not a defense. It closes mechanism 1 and leaves mechanism 2 wide open. Module 05 is entirely this mechanism.

Mechanism 3 — URI schemes code as a URL

Certain sinks navigate to a URL. If the URL's scheme is javascript:, the "navigation" executes code; if it is data:text/html, the browser renders an attacker-authored document. Sinks include href, src, action, formaction, xlink:href, and JS APIs like location.href= and window.open().

<a href="javascript:alert(1)">click</a>
<iframe src="data:text/html,<script>alert(1)</script>">
<form><button formaction="javascript:alert(1)">go

What stops it: scheme allowlisting (after entity decoding — see Module 02 case 5) and CSP. Module 06 is this mechanism.

What stops it: Trusted Types (forces sinks to accept only vetted typed objects), safe sink choice (textContent not innerHTML). Module 09 is this mechanism.

Mechanism 5 — Context escape + reparse the subtle one

Two related ideas:

  • Context escape: your input lands inside some context (an attribute value, a JS string). You supply the bytes that end that context and start a code-bearing one — the leading "> in "><svg onload=alert(1)> closes an attribute and a tag, then opens your own.
  • Reparse / mutation (mXSS): a string that is inert when a sanitizer inspects it, but becomes active when the browser re-parses its own serialization (Module 02's reserialize(parse(x)) ≠ x). The canonical trigger is content that is foster-parented or that changes meaning when moved between HTML and foreign (SVG/MathML) contexts.
"><svg onload=alert(1)>            <!-- escapes an attribute context -->
</script><script>alert(1)</script>  <!-- escapes a JS string context -->
<noscript><p title="</noscript><img src=x onerror=alert(1)>"> <!-- mXSS-style reparse -->

What stops it: correct contextual encoding for the exact context, and DOM-based (tree-level) sanitization that is idempotent under re-serialization — string sanitizers structurally cannot guarantee this. Modules 08 and 13 are this mechanism.
