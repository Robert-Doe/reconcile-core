Module 12 · the case against denylists

Filter Evasion & Obfuscation attack

This module exists to prove one claim empirically: string / regex matching on payloads is an unwinnable defense. The input space is adversarial and the browser has a hundred equivalent ways to spell any payload.

The target filter

Module 12's /waf-search (waf_sim.py) reflects q unencoded, but first blocks this case-insensitive denylist:

<script     |  </script  |  onerror  |  javascript:  |  alert

It looks like it covers "the dangerous stuff." Your task: pop an alert five different ways. Each way attacks a different assumption the filter makes.

5. Encoding across a decode boundary — the classic mismatch

The most important idea: a filter and the browser decode at different times. If your payload is decoded after the filter runs, the filter inspected a harmless-looking string. Examples of decode boundaries:

Why this is the pivotal defensive lesson

Every bypass above exploits the same structural flaw: the filter and the browser disagree about what the string means. The filter matches bytes; the browser parses and decodes them through a stateful, multi-context, error-recovering machine (Module 02). You cannot enumerate the browser's equivalence classes with a denylist, and each new spec adds more. This is the reason serious defenses are:

  • Allowlist, not denylist (permit a tiny known-safe set).
  • Contextual output encoding (make the byte inert for its exact context, regardless of how it's spelled).
  • Capability-based (CSP / Trusted Types stop execution, so it doesn't matter how cleverly the payload is spelled).
