Module 02

How Browsers Parse HTML — The Root of Everything

You cannot design a defense against XSS until you understand that the HTML parser does not reject bad input — it recovers from it, deterministically, and that recovery is the attack surface.

1. The two-stage pipeline

The HTML Standard defines parsing as two coupled stages that run together, byte by byte:

bytes ──▶ [ Tokenizer ] ──tokens──▶ [ Tree Construction ] ──▶ DOM tree
              (a state machine)          (a stack of open elements +
                                          25 "insertion modes")

Stage 1: the Tokenizer (a state machine)

The tokenizer walks the input one code point at a time, moving between states. A few states that matter enormously for XSS:

StateEntered byWhy it matters
Datadefault textOnly < and & are special. This is where < starts a tag.
RCDATAinside <title>, <textarea>Tags are inert but entities still decode. You cannot open a tag, but & works.
RAWTEXTinside <style>, <xmp>, <noframes>Neither tags nor entities are special — only the matching end-tag. Sanitizers often mishandle this.
Script datainside <script>A famously baroque set of sub-states (<!--, <script escapes) that enable script-in-script confusion.
Tag open / Attributeafter <Where tag names and attributes (including on* handlers) are read.
Key consequence #1. The same characters mean different things in different tokenizer states. A sanitizer that scans a flat string without tracking state is reasoning about a fiction. The browser tracks state; your regex does not.

Stage 2: Tree Construction (insertion modes + the stack)

Tokens are fed into a state machine with ~25 insertion modes ("initial", "in head", "in body", "in table", "in select", …) plus a stack of open elements and a list of active formatting elements. This stage is what:

  • Auto-closes tags (<p>a<p>b → two siblings).
  • Foster-parents illegal table content out of the table.
  • Runs the adoption agency algorithm to untangle misnested formatting tags (<b><i></b></i>).
  • Switches into foreign content for <svg>/<math>, where different rules (case sensitivity, self-closing, CDATA) apply.
Key consequence #2. The tree the browser builds is frequently not the tree your input literally describes. Nodes get moved, closed, split, and re-nested. Any defense that sanitizes the string but the browser stores the tree has a semantic gap — and that gap is exactly mutation XSS (Module 13).

4. Why the preload scanner also reads your bytes early

While the main parser is still building the tree, the browser runs a speculative "preload scanner" that races ahead to find subresources (<img>, <script src>, <link>) so it can start fetching them before the main parser reaches them. Two security implications you will revisit:

  • Injected markup can trigger fetches before the page finishes loading — an injected <img src> or dangling-markup attribute can begin exfiltrating as it parses (Module 08's dangling-markup theft).
  • The scanner sees the raw tokenized markup, so injection that only looks safe after later JS runs may already have leaked.
